# 音声入力オーケストレーター基盤 (Voice Input Orchestrator)

## Summary

音声による入力をリアルタイムに受け取り、AI要約を経てオーケストレーターへ渡す汎用基盤を構築する。本チケットの本質はカスタムコマンドの作成ではなく、**音声入力の汎用ルーティング基盤**である。カスタムコマンド作成はこの基盤を利用した具体例の1つであり、別チケットで対応する。

## Background

現在の「音声入力インプット」(Alt/Option ダブルタップ) はカーソル位置への文字列入力 (バッファ&フラッシュ) に特化しており、AIとの対話やエージェントへの指示入力には使えない。今後、音声UIが主要な操作手段となることを見据え、以下の要件を満たす汎用基盤が必要である：

- 発話内容をリアルタイム文字起こし
- AI要約による発話の確定
- オーケストレーターによる処理振り分け
- 1つのオーバーレイ内で完結する対話セッション

## Scope

### 1. 音声認識エンジンの汎用化（バックエンドのみ）

既存の「音声入力インプット」と新設する「音声入力ルーティング」で、**バックエンドのリアルタイム音声認識（STT）機構**を共通化・抽象化する。

**共通化しないもの（＝既存フロントエンドには一切触れない）**：
- 音声入力インプットのトリガー（Altダブルタップ）
- 音声入力インプットのUI/UX（バッファ&フラッシュ、カーソル位置への入力）
- 音声入力インプットのフロントエンド実装（Vueコンポーネント）

### 2. 音声入力オーバーレイ（独立コンポーネント）

- キー操作で起動する全画面オーバーレイ
- **デザインは既存の「音声入力インプット」用オーバーレイ (`web/src/components/tools/OverlayView.vue`) を踏襲し、それをベースにカスタマイズする**
  - 既存オーバーレイのコンテナ構造、背景スタイル（半透明ガラス効果 `backdrop-filter: blur`）、フォント（MPLUSRounded1c）、アニメーション（scale + border-radius 遷移）を継承
  - その上で、音声入力ルーティング専用のUI要素（対話履歴表示、マークダウンレンダリング、オーケストレーター処理中アニメーション等）を追加する
- **閉じるボタン**: 既存 OverlayView.vue と同様の閉じるボタンを配置。セッションの明示的終了はこのボタンのみ（自動クローズしない、タイムアウトしない）
- 発話内容をリアルタイムで文字起こし表示
- オーケストレーターからの応答をマークダウンレンダリングで表示
- セッション全体の会話がスクロールで閲覧可能
- **デザイン**:
  - ユーザー発話: 小さめの文字、半透明グレーの背景（ブレーン状）で判別可能に
  - AI応答: 背景なし、メインコンテンツとして大きく表示
- **処理中アニメーション**:
  - 独立したコンポーネントとして切り出し、後で容易に差し替え可能にしておく
  - イメージ: 画面中央にゆらゆらと動きながら大小に変形する球が、生き物のように上下に浮遊する
  - 本チケットでは凝った実装は不要。後で丁寧に差し替えることを前提とした最小実装でよい

### 3. キーバインド（音声入力ルーティング専用トリガー）

- **トリガー**: Ctrl+Alt（Windows）/ Control+Option（macOS）の同時押し
- **順序非依存**: どちらの修飾キーを先に押しても検出する（「片方のみ→両方」の状態遷移で判定）
- **150ms クールダウン**: 同時押しを確定させるための猶予（誤発火防止）
- 新しい HotkeyAction 種別を追加（`OrchestratorInput` 等）
- キーバインドは設定ファイルで変更可能にする
- 既存の「音声入力インプット」(Alt/Option ダブルタップ) とは完全に独立したバインドとする

### 4. 対話モデル（Tap-to-Talk + 複数ターン）

- **セッション開始**: Ctrl+Alt 同時押し → オーバーレイ表示・録音開始
- **発話確定**: 再度 Ctrl+Alt 同時押し → 録音終了・オーケストレーターへ送信
- **複数ターン**: オーケストレーターの応答後、さらに Ctrl+Alt 同時押しで追加発話可能
- **セッション終了**: オーケストレーターがタスク完了と判断した時点で、ユーザーに「タスク完了と判断しました。」旨を伝える。セッションは自動では閉じず、タイムアウトもしない。ユーザーがオーバーレイの閉じるボタンを押して明示的に閉じるか、追加の発話をしてセッションを継続する。
- セッション内の会話履歴は文脈として維持される

### 5. オーケストレーター（本チケットではモック実装）

**本チケットでは、オーケストレーターを `trait` として抽象化し、そのモック実装までを行う。**

抽象化の理由：
- **モックとの差し替えがゼロコスト**: 将来の本実装（RealOrchestrator）に切り替えても、UIレイヤーのコード変更が一切不要
- **非同期対応**: 本実装ではLLM呼び出し等の非同期処理が発生するため、`#[async_trait]` で統一
- **テスト容易性**: モックを注入して結合テストが書ける。完了判定テストも MockOrchestrator の挙動を変えるだけで様々なパターンをカバー可能
- **拡張性**: 新たな Orchestrator 実装を追加しても、既存コードに影響を与えない

具体的なオーケストレーター実装（エージェント構成、タスク振り分けロジック等）は別途議論・実装する。

#### モック実装の動作仕様

MockOrchestrator は以下の状態を持つ：

```rust
struct MockOrchestrator {
    session_id: String,  // 初回 process() 呼び出し時に自動発番
    rally_count: u32,    // 同一セッション内のラリー回数
}
```

| イベント | 動作 |
|---------|------|
| 初回 process() 呼び出し | `session_id` を自動生成（UUID等）。`rally_count` を 1 に設定。入力テキストに `"[Orchestrator Echo]: {入力テキスト}"` を付加してエコーバック |
| 2回目以降の process() 呼び出し | `rally_count` をインクリメント。エコーバック |
| rally_count == 3 | エコーバックに加えて、完了メッセージ `「タスク完了と判断しました。」` を追記し、`task_completed: true` を返す |
| rally_count >= 3 の状態でさらに発話 | `rally_count` を 0 にリセットし、新たにカウントを開始（何度でも3回ラリー可能） |
| 空テキストが入力された場合 | `Err(OrchestratorError::EmptyInput)` を返す |

#### インターフェース定義（案）

オーケストレーターは、**音声認識結果のテキストを受け取り、要約・加工し、処理結果を返すパイプライン**として定義する。モックは要約処理を行わず単純エコーするが、トレイトのシグネチャは本実装で要約・ルーティング・エージェント呼び出しが可能な構造にする。

```rust
/// オーケストレーターへの入力
struct OrchestratorInput {
    /// 生の音声認識テキスト
    raw_text: String,
    /// オーケストレーターが生成するセッションID（初回入力時に自動発番）
    session_id: String,
}

/// オーケストレーターからの出力
struct OrchestratorOutput {
    /// ユーザーに表示する応答テキスト（マークダウン形式）
    response_text: String,
    /// タスク完了フラグ（true の場合、UI は完了通知を表示する）
    task_completed: bool,
}

#[async_trait]
trait Orchestrator: Send + Sync {
    /// ユーザー発話をパイプラインで処理し、応答を返す。
    ///
    /// パイプラインの流れ（本実装時）:
    ///   1. 入力テキストの正規化・前処理
    ///   2. AI要約（発話意図の抽出）
    ///   3. ルーティング（適切なエージェント/処理へ振り分け）
    ///   4. 応答生成
    ///
    /// session_id の責務:
    /// - オーケストレーターが session_id を生成・管理する
    /// - 初回の process() 呼び出し時に自動発番し、同一セッション内では同じ ID を使い続ける
    /// - 本チケットでは DB 永続化は行わず、メモリ上のモック管理で十分
    async fn process(&mut self, input: &OrchestratorInput) -> Result<OrchestratorOutput, OrchestratorError>;
}

/// オーケストレーターエラー
enum OrchestratorError {
    /// 音声認識テキストが空
    EmptyInput,
    /// パイプライン処理失敗（本実装時: AI要約失敗等）
    PipelineFailed(String),
    /// 内部エラー
    Internal(String),
}
```

## Investigation

### 確認済みの既存実装

1. **ホットキー基盤** (`src/hotkey_mac.rs`, `src/hotkey_win.rs`, `src/hotkey_win_hook.rs`)
   - macOS: CGEventTap によるグローバルキーフック（Accessibility 権限必要）
   - Windows: rdev + WH_KEYBOARD_LL + GetAsyncKeyState の3経路併用
   - いずれも修飾キーの状態追跡が実装済みであり、Ctrl+Alt/Control+Optionの検出に流用可能

2. **HotkeyAction enum** (`src/types.rs`)
   - 現在: `Start`, `Correct`, `Summarize`, `BufferFlush`
   - ここに `OrchestratorInput` を追加する

3. **HotkeyConfig** (`src/mycute_settings.rs`)
   - 現在: `correct`, `summarize`, `buffer_start`, `buffer_flush`
   - ここにオーケストレーター用のキーバインド設定を追加する

4. **音声認識エンジン** (STT モジュール)
   - 現在の「音声入力インプット」で使用中の実装の所在を確認し、抽象化対象を特定する

### 未確認（後日調査）

## Technical Decisions (合意済み)

| 項目 | 決定内容 |
|------|---------|
| トリガーキー | Ctrl+Alt (Win) / Control+Option (Mac) |
| キー検出方式 | 状態遷移検出（片方のみ→両方）、順序非依存 |
| クールダウン | 150ms（同時押し確定のための猶予） |
| 録音方式 | Tap-to-Talk（押下で開始、再押下で終了・送信） |
| セッション終了 | オーケストレーターが完了判断 → ユーザーに通知 → ユーザーが明示的に閉じるか追加発話 |
| オーバーレイ種別 | 全画面（既存 OverlayView.vue と同様の scale + border-radius アニメーション）、チャット形式 |
| ユーザー発話表示 | 小さめ文字 + 半透明グレー背景 |
| AI応答表示 | 背景なし、メイン表示 |
| 処理中アニメーション | 独立コンポーネントとして切り出し（後で差し替え可能）。イメージ: 浮遊する球 |
| マークダウン | 専用のOSSライブラリでHTML変換して表示（要選定） |
| 音声認識エンジン | 既存「音声入力インプット」と**バックエンド STT 実装のみ**共通化。フロントエンドは新設。 |

### ユニットテスト計画（案）

1. **キーバインド検出**
   - Ctrl+Alt 同時押し → OrchestratorInput 発火（macOS/Windows 両方）
   - Ctrl のみ押下 → 発火しない
   - Alt のみ押下 → 発火しない
   - 順序逆転（Alt→Ctrl）でも発火すること
   - クールダウン150ms未満の瞬間的な同時押し → 発火しない
   - 片方のキーを離したら再度両方押すまで発火しない

2. **オーバーレイコンポーネント**
   - 起動 → 表示・録音開始
   - 発話確定 → テキスト送信・文字起こしクリア
   - 応答表示 → マークダウンが正しくレンダリングされる
   - スクロール → 会話履歴がスクロール可能
   - 閉じるボタン → セッションが明示的に終了する
   - 処理中アニメーション → コンポーネントが独立して存在し、表示/非表示が制御できる

3. **オーケストレーターインターフェース**
   - 入力値/出力値の型が正しいこと
   - MockOrchestrator がエコーバックを返すこと
   - rally_count が 1, 2, 3 と正しくインクリメントされること
   - rally_count == 3 時に完了メッセージが追記され、task_completed == true となること
   - rally_count >= 3 の状態でさらに発話すると 0 にリセットされること
   - 空テキストを入力 → Err(EmptyInput) が返ること
   - session_id が初回呼び出し時に自動生成されること
   - 同一セッション内で session_id が変わらないこと
