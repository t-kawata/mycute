# Tauri v2 移行設計指針

## Windows オーバーレイ問題の扱いについて

> [!IMPORTANT]
> **Windows 環境においてオーバーレイが表示されない既知の問題は、現在の eframe (egui) 実装では修正せず、本 Tauri 移行作業の中で根本解決を図る。**
>
> 理由：
> 1. **作業の重複回避**: eframe 固有の描画問題を解決しても、その直後に UI 基盤を Tauri へ刷新するため、その作業は無駄になる。
> 2. **基盤による解決**: Tauri (WebView2) を採用することで、OS 標準のウィンドウ制御機能を利用でき、透過やクリック透過といった複雑な挙動をより確実に、かつプラットフォーム間で対称的に実装できる。
> 3. **リソースの集中**: 不安定な旧実装のパッチ当てではなく、最終的な完成形となる Tauri 実装にリソースを集中させ、開発効率を最大化する。

## Mac/Windows 2台体制による開発プロトコル

本作業は、Mac（AI常駐）と Windows（ユーザー操作）の2台のPCをGitHub経由で同期しながら進める。

### 1. 同期コマンドの限定
環境間の不整合やコンフリクトを避けるため、同期は以下の `Makefile` コマンドのみを使用して行う。

- **送り側 PC: `make push`**
  - バージョンをインクリメントし、全変更を `master` ブランチへ Push する。
- **受け側 PC: `make pull-force`**
  - リモートの最新状態を `fetch` し、ローカルの変更を破棄してリモートと強制一致 (`reset --hard`) させる。

### 2. コマンド実行の指示と依存関係の解決
- **ツールのインストール (`cargo install`)**:
  - 新しいツールを導入する際は、Mac側で実行するだけでなく、ユーザーに対してWindows側での実行も明示的に指示し、両環境のツールバージョンを揃える。
- **依存関係の追加 (`cargo add`)**:
  - クレート追加時は、そのクレートが Windows/Mac 両方でビルド可能であるか、またはプラットフォーム固有の依存関係（SDK等）が必要ないか、AIが事前に調査し、必要な手順をユーザーに指示する。

### 3. AI（Mac）とユーザー（Windows）の連携
- 私は直接 Windows を操作できないため、Windows 固有のビルド確認や動作検証が必要な場合は、具体的なコマンド（例：`make build`）を添えてユーザーに指示を出す。
- ユーザーは Windows 側での作業結果（成功/失敗・ログ）を AI に報告し、AI はそれをもとに次のアクションを決定する。

## 目的
`mycute` のデスクトップアプリケーション配布を Mac/Windows で統合し、UI（設定画面・ヘルプ・オーバーレイ）を Web 技術でモダン化する。その際、既存の高度な Rust 音声処理エンジンおよび OS 固有バックエンド（Swift/C#）を一切破壊せずに移管する。
## 基本方針
1. **Tauri v2 統合構成 (Minimal Dir Structure)**:
   - `src-tauri` ディレクトリを新設せず、プロジェクトルートをそのまま Tauri バックエンドとして利用する。
   - 既存の `Cargo.toml` に Tauri 依存関係を追加し、Tauri は「高性能な GUI ライブラリ」のひとつとして扱う。
2. **既存実装の破壊的変更の禁止**:
   - 既存の `main.rs` におけるモード分岐（`Mode::Vp`, `Mode::Settings` 等）を維持する。
   - `Mode::CL` を新設し、ランタイム引数や設定によって新旧 UI を切り替え可能にする。
3. **ロジックと UI の完全分離**:
   - `src/` 配下の音声認識、LLM、ホットキーロジックをライブラリ化（内部モジュール化）し、egui と Tauri の両方から参照可能にする。
4. **チック（Tick）の適切な再配置**:
   - 音声認識の安定性に直結するバックエンドロジックのチックは Rust 側で維持し、UI 表示関連のチックはフロントエンド側に移管して安全性を確保する。
5. **ビルド・同期パイプラインの自動化**:
   - `make run` や `make build` 実行時、Quasar プロジェクトのビルド（SPA生成）を自動実行し、その成果物を Tauri 用ディレクトリに物理的に同期してから Rust 側のビルドを開始するフローを `Makefile` で構築する。
## アーキテクチャ構成
### バックエンド (Rust/Native)
- **Core Engine**: 既存の `stt`, `llm`, `hotkey` モジュール。
- **FFI Layer**: Mac (`SpeechHelper.a`) および Windows (`SpeechHelper.staticlib`) の既存ネイティブコード。
- **Tauri Bridge**: JS から呼び出すための `tauri::command` ラッパー群。
### フロントエンド (Web)
- **UI Framework**: **Quasar (Vue.js 3)** を使用。マテリアルデザイン等のモダンなコンポーネントを活用して高品質な UI を構築する。
- **Overlay Window**: Tauri の透明・クリック透過ウィンドウ機能を用いて、現在のカーソル追従オーバーレイを再実装。
### チックの扱い (Tick Handling)
- **Rust バックエンド (Core)**: VAD（無音検知）やタイムアウト監視など、音声認識の「脳」にあたるチックは、既存の Rust バックグラウンドループ内で引き続き正確に実行する。
- **ウェブビュー (Quasar)**: スナックバーの消去タイマーや描画リフレッシュなど、UI の見栄えに関するチックは Vue/JS 側のタイマー機能に移管し、描画パフォーマンスを最適化する。
## 注意事項
- **ビルドパス**: `Makefile` で管理されている既存のビルドパイプライン（特に Windows 側の AOT ビルド）と Tauri のビルドプロセスが干渉しないよう慎重に統合する。
- **ホットキー**: `rdev` 等の既存ホットキー監視スレッドと Tauri のメッセージループが同一バイナリ内で安全に共存することを確認する。
## 安全な移管プロトコル (Surgical Migration methodology)
本プロジェクトにおける Tauri への移管は、既存の安定した「音声認識エンジン」に影響を与えないよう、極めて慎重に行う必要がある。そのため、AI による「一からのコード生成」ではなく、以下の手順を厳守する。
### 1. OS レベルでのファイルコピー (`cp` コマンドの活用)
既存のロジックを移管・拡張する場合、AI のエディタツールで新規作成するのではなく、OS の `cp` コマンドを使用して物理的な複製を作成する。
- **理由**: AI の読み取り・書き出しプロセスを介さず、インデント、改行コード、微細なコメント、既存のロジックを 100% 保持するため。
- **操作**: `run_command` を使用し、ビット単位で正確なコピーを生成する。
### 2. 最小限の外科的編集 (Minimal Surgical Edits)
コピーされたファイルに対し、Tauri との接続に必要な変更（`#[tauri::command]` の付与や、戻り値のラップ等）のみをピンポイントで適用する。
- **理由**: 「いつの間にかロジックが変わっていた」という事故を物理的に防ぎ、差分を最小限に抑えることで検証を容易にするため。
### 3. デュアル・ランタイムの維持
`main.rs` の分岐構造を最大限に活用し、従来の egui 版ロジックと新しい Tauri 版ロジックを共存させる。
- **目的**: 万が一 Tauri 側で予期せぬ挙動が発生した場合でも、即座に従来の動作（安定版）と比較・フォールバックできるようにするため。
- **検証**: 新しいロジックが従来のロジックと同等の安定性と精度を維持していることを、常に「横並び」で確認可能にする。
### 4. 事故防止への配慮
Tauri への移行は「UI の差し替え」であり、エンジンの再実装ではない。この境界線を明確に保つため、コアロジックを含むファイルに変更を加える際は、その意図と影響範囲を常に明文化し、既存の音声入力体験を損なわないことを最優先とする。
