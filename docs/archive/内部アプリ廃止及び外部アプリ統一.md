# 内部アプリケーションの廃止と外部アプリケーション基盤への統一

## 1. コンセプトと目的：なぜ「統一」するのか

### 背景：二重管理の課題
現在、MYCUTE にはシステムに深く組み込まれた「内部アプリケーション（設定画面やホーム画面など）」と、外部から読み込まれる「外部アプリケーション（WebFrame）」という2つの異なる実装モデルが混在しています。この状態は、開発者にとって「内部用API」と「外部用SDK」の二重メンテナンスを強いるだけでなく、外部開発者に対して「OS開発者だけが使える特権的な機能」が存在するという不透明さを生んでいました。

### 解決策：ドッグフーディングによる基盤統一
この課題を根本から解決するため、「内部アプリケーション」という特権的な区分を完全に廃止します。OSの開発者自身も、外部のサードパーティ開発者と全く同じ制約、同じ SDK、同じプロキシ経由の通信ルールに従って、設定画面やホーム画面を開発します。

この方針（Dogfooding）には以下の狙いがあります：
1.  **API の品質向上**: OS開発者が自らユーザーとして SDK を使い倒すことで、バグや使いにくさが即座に発見され、API の品質と機能が飛躍的に向上します。
2.  **エコシステムの健全化**: 「OS内蔵アプリでできることは、外部アプリでもできる」ことが保証され、サードパーティ開発者にとって透明性が高く、参入しやすいプラットフォームになります。
3.  **セキュリティの実証**: 重要なシステム機能（設定変更など）を SDK 経由で実装することで、そのセキュリティ機構が実戦環境で常に検証されることになります。

## 2. アプリケーション定義の再構築

今後、MYCUTE における「アプリケーション」とは、以下の条件をすべて満たすものを指します。例外は認められません。

1.  **物理的な独立性**: すべてのアプリは、HTML/JS/CSS で構成される独立した Web ページ（または Web アプリケーション）として存在しなければならない。
2.  **実行環境の統一**: すべてのアプリは `WebFrame` コンポーネント（iframe）内で実行され、必ず MYCUTE プロキシを介して表示されなければならない。
3.  **インターフェースの統一**: システム機能へのアクセスは、いかなる場合も `sdk-ts` (MYCUTE SDK) を介して行わなければならない。Vue コンポーネントの直接インポートや、Rust バックエンドへの直接アクセスは禁止される。

## 3. 今後の進め方（概要）

本ドキュメントは、この大方針に基づいた具体的な実装計画を策定するためのベースとなります。
現時点では「概念の統一」を合意事項とし、具体的なコード修正や移行ステップについては、今後の対話を通じて決定します。

## 4. 配備手法（デプロイメント）の3つのレイヤー

「すべてのアプリを統一的に扱う」といっても、物理的なファイルの在り処は様々です。MYCUTE では、アプリの実体が存在する場所に応じて以下の3つのレイヤーを定義しますが、利用者・開発者からは**すべて同一の仕組み（URL）でアクセス可能**であるように抽象化します。

### レイヤー1: プリインストール（Rust バイナリ同梱型）
**「OSを買った直後から使えるアプリ」**
設定画面やホーム画面など、OS に不可欠な基本機能を提供するための形態です。これらのアセット（ビルド済みの SPA）は Rust のバイナリファイルの中に直接埋め込まれます。
- **仕組み**: プロキシサーバー内に組み込まれた「内蔵ハンドラ」が、メモリ上のデータをあたかも Web サーバーからのレスポンスのように振る舞って返却します。
- **メリット**: ユーザーによるインストール作業が不要で、オフラインでも確実に動作し、誤って削除されるリスクがありません。

### レイヤー2: ローカルインストール（パッケージ型）
**「ダウンロードして使う、高速・セキュアなアプリ」**
ユーザーがストアや配布サイトからダウンロードして追加する形態です。SPA のアセット一式（`.mycute` パッケージ）を、OS 内のストレージ（ディスク）に保存します。
- **仕組み**: プロキシサーバーが、ディスク上の特定ディレクトリをドキュメントルートとしてファイルを読み取り、配信します。
- **メリット**: 一度ダウンロードすれば通信環境に依存せず高速に動作し、プライバシーも守られます。

### レイヤー3: リモートホスト（URL 参照型）
**「常に最新、インターネット上のサービス」**
既存の Web サービスや、頻繁に更新されるクラウド型アプリを利用するための形態です。
- **仕組み**: 従来の Web ブラウザのように、インターネット上のサーバーへアクセスします。ただし、必ず MYCUTE プロキシを経由することで、SDK の注入やセキュリティポリシーの適用を行います。
- **メリット**: サーバー側の更新が即座に反映され、大規模なバックエンドを持つサービスもそのまま利用可能です。

## 5. アプリケーションの識別：三位一体の ID (The Trinity)

アプリの名前（例：「カレンダー」「設定」）は重複しやすく、衝突の原因となります。これを物理的に回避し、P2Pネットワーク上で安全にバージョン管理を行うため、アプリケーションは以下の3つの要素によって厳格に定義されます。

1.  **`global_app_id` (UUID v4)**
    - **役割**: アプリケーションの「恒久的な身元（ID）」。
    - **不変性**: バージョンアップしても変わりません。設定ファイルやデータはこのIDに紐付きます。
    - **URL**: `https://{uuid}.mc.shyme.net`

2.  **`global_app_version` (String: `00000.00.00`)**
    -   **「世代」**: 人間が進化を理解するためのバージョン番号です。
    -   *役割*: 固定長・ゼロ埋めフォーマット（例: `00001.02.03`）により、文字列比較だけで確実に新旧を判定できます。ユーザーは「最新版」だけでなく「特定のバージョン」を指定してダウンロードできます。

3.  **`global_app_hash` (Signature Hash)**
    - **役割**: ファイル実体の「指紋」。
    - **重要性**: P2Pネットワーク上でファイルを特定し、改ざんがないことを保証する唯一の数学的根拠です。

## 6. データベースによる「動的マッピング」

「どの UUID が、どのレイヤーに属し、どこに実体があるのか」という情報は、静的な設定ファイルではなく、**データベース（REST API用と共通）** で一元管理します。

- **統合されたルックアップ**:
  プロキシサーバーはリクエスト (`{uuid}.mc.shyme.net`) を受けると、まずデータベースを参照します。
  - DB:「その UUID は『ローカルインストール』で、パスは『/disk/apps/xyz』だよ」
  - プロキシ:「了解、そのパスからファイルを返します」
  
- **即時反映**:
  アプリのインストールや削除は、データベースのレコード操作（INSERT/DELETE）のみで完結します。プロキシサーバーを再起動することなく、動的にアプリの追加・削除が反映される仕組みです。

## 7. 信頼と検証（Trust & Verification）：安全な流通のエコシステム

MYCUTE は単にアプリを動かすだけでなく、「誰が作ったか」「安全か」を保証するエコシステムを提供します。その中心となるのが、MYCUTE サービスの運営母体による **中央認証局 (Root CA)** モデルです。

### 信頼の連鎖 (Chain of Trust)
アプリがユーザーの手元に届くまで、以下のような信頼の連鎖が構築されます。

1.  **開発者の本人確認**:
    アプリ開発者（MYCUTE ユーザー）は、初回起動時に生成された自身の公開鍵を自身のノード（またはCAノード）に登録します。さらに、事務局による本人確認手続きを経ることで、その鍵に「Verified（認証済み）」情報が付与されます。
    
2.  **署名付きパッケージ (.mycute)**:
    アプリをビルドする際、開発者の秘密鍵を使ってパッケージ全体にデジタル署名が行われます。これにより、「誰が作ったか」と「改ざんされていないか」が数学的に保証されます。
    
3.  **インストール時の検証と情報の提供**:
    ユーザーがアプリをインストールしようとすると、システムは以下の確認を行います。
    - **整合性チェック (必須)**: ファイルが壊れていないか、ハッシュ値と署名を照合します。これはシステム保護のために必須のプロセスです。
    - **信頼性情報の照会 (任意・情報提供)**: 署名した開発者の公開鍵が、信頼されたCAによって「Verified」になっているかを確認します。
    
    *重要*: 認証は、インストールを物理的にブロックするものではありません。あくまで「この開発者は事務局が身元を確認済みである」という客観的な情報を提供するためのものです。認証されていないアプリをインストールする際には、システムがアラート等で「未認証の開発者によるアプリです」と通知することで、ユーザーが自己責任で判断できる材料を提供します。

## 8. REST API 中心のアーキテクチャ

MYCUTE のアプリケーション基盤は、その設計当初からすべての主要な操作（ビルド、登録、検証）を **REST API** に集約する方針をとっています。これにより、設定画面などの GUI からのシームレスな操作を可能にし、同時に外部ツールやシステムとの柔軟な連携を保証します。

### アイデンティティ & キー管理 API
信頼の基点となる「鍵」を管理します。
-   **`POST /v1/identity/register`**:
    自身の公開鍵を中央サーバーへ登録します（初回起動時に自動実行）。
-   **`GET /v1/identity/keys/{id_or_pubkey}`**:
    ある公開鍵が誰のものか、そして事務局によって「本人確認済み (`is_verified_by_registry: true`)」とされているかを照会します。

### アプリケーション管理 API
データベース上のアプリ情報を操作します。
-   **`POST /v1/apps`**:
    新しいアプリ定義をデータベースに追加します（インストールの最終工程）。
-   **`GET /v1/apps/{uuid}`**:
    プロキシサーバーがアクセス時に使用する、UUID から実体パスへの解決を行います。
-   **`GET /v1/apps`**:
    インストール済みアプリの一覧を返します。

### ビルド & 配布・インストール API
アプリのパッケージングと導入を担当します。
-   **`POST /v1/apps/build`**:
    **「ディレクトリを .mycute に変換する」**機能です。
    指定された SPA のディレクトリ（例: `dist/`）を、**Zstandard (zstd)** で高圧縮し、自身の秘密鍵で署名を付加して、単一のバイナリファイル (`.mycute`) を生成します。
    -   *特徴*: zstd の採用により、展開時も全解凍することなく、必要なファイルだけを高速にランダムアクセスで読み出せます。
    
-   **`POST /v1/apps/verify`**:
    入手した `.mycute` ファイルの署名を検証し、さらに中央サーバーへ問い合わせて開発者の信頼性情報を取得します。取得された「本人確認済みか否か」の情報は、インストール時のユーザー判断（アラート表示など）に利用されます。
    
-   **`POST /v1/apps/install`**:
    `.mycute` ファイル、またはリモート URL をシステムに正式に登録します。登録前に `verify` を実行し、整合性が確認されればインストールは実行されます（信頼性情報の有無に関わらず、最終的な実行可否はユーザーに委ねられます）。

## 9. 信頼の中核：オーナー事務局と中央認証局の権限委譲モデル

MYCUTE のエコシステムにおける信頼の構造は、以下の「Pull型 (Retrieval-based)」の権限モデルによって成り立っています。

#### 階層1: オーナー事務局（The Owner Bureau）
-   **主体**: MYCUTE の完全なオーナー（開発者：川田氏）。
-   **権限**: 唯一無二のルート権限（5つの特別キー）を保有。
-   **役割**: CA を任命することだけが役割です。
-   **操作**: `POST /v1/owner/assignca` で CA 候補から公開鍵を受け取り、それに対しオーナー秘密鍵で署名を施した**「CAトークン（デジタル任命証）」**を交付します。

#### 階層2: 中央認証局（The Central Certificate Authority）
-   **主体**: オーナーから任命された運用チーム（または運用システム）。
-   **権限**: 自身の鍵ペアと、オーナーから授与された「CAトークン」を保有。
-   **役割**: 実際のアプリ開発者の本人確認（eKYC）を行い、証明書を発行します。
-   **操作**:
    - `GET /v1/identities/retrieve/{pubkey}`: 開発者に対して、署名済みの証明書と、自身の正当性を示す「CAトークン」をセットで提供します。

---

### 「5つの特別キー」による権限管理
ルート権限を持てるのは、オーナー自身だけが物理的に保有する **5つの特別なキーペア** のうち、少なくとも1つを持っている人物だけです。

**採用アルゴリズム: Ed448 (Goldilocks)**
MYCUTE エコシステム内のすべての鍵は、**Ed448 (Goldilocks)** 曲線を用いた署名方式に統一します。

1.  **オーナー事務局キー**: ルート権限管理用 (5本)。
2.  **中央認証局キー**: CA が自身の身元を証明し、開発者を署名するためのキー。
3.  **アプリ開発者キー**: 各開発者が **`.mycute` パッケージへのデジタル署名** を行うために使用するキー。
4.  **ユーザー識別キー (Identity)**: 全てのノードが持つアイデンティティ証明用キー。

### 管理者用 REST API エンドポイント (概要)
-   **`POST /v1/owner/assignca`**: CA候補に対する CAトークンの発行。
-   **`POST /v1/identities/apply`**: 開発者による公開鍵の登録申請。
-   **`GET /v1/identities/retrieve/{pubkey}`**: 開発者による署名済み証明書・CAトークンの取得。

        1.  **DB Transaction Start**: `db.begin()`

        3.  **Config Update (In-Memory)**: Config 構造体の値を `new_key` で暗号化した値に置換。
        4.  **File Prepare**: `settings_mac.json.new` に新 Config を書き出し。
        5.  **Critical Section**:
            - `fs::rename("settings_mac.json.new", "settings_mac.json")` (Atomic)

            - 失敗 (Rename不可) -> `tx.rollback()`, ログ出力して終了（旧鍵のまま維持）。

    - [x] **Step 4: Journaling & Recovery**

        - 不整合時は、旧鍵と新鍵の両方で復号を試行し、正しい方に統一する修復プロセスを走らせる。

### Phase 5.5: [追加/詳細化] 分散型信頼システムと二次投票の完全実装 (Trust & Voting Core)
「情報の不変性」だけでなく「熱意の定量化」を検証可能な形で実現するための、DB・API・ロジックの拡張計画です。Phase 6 以降の基盤となる重要フェーズであるため、データ構造と計算ロジックを、その「意図（Why）」と「方法（How）」を含めて詳細に定義します。

#### 5.5.1. 物理的基盤: DBスキーマの拡張 (Schema Evolution)
情報の即時性と完全なポータビリティを実現するため、`apps` テーブルと `identities` テーブルを拡張します。

118. [ ] **DB**: 新規マイグレーション `mYYYYMMDD_HHMMSS_expand_apps_for_trust.rs` を作成する
    - [ ] `apps` テーブルへのカラム追加:
        - [ ] `author` (String, Nullable): マニフェストから抽出した著者名。表示用。
        - [ ] `verified_level` (Integer, NotNull, Default=0): 構造的信頼レベル。
            - **目的**: アイデンティティの「身元証明の強度」を物理的に記録し、不当な昇格や詐称を防ぐための基底値です。
            - `0`: **Unknown** (署名なし/検証失敗) - まだ何の証明もされていない状態。
            - `1`: **Self-Signed** (**L1** / Proof of Cost) - 自らコストを払って存在するが、CAによる承認を受けていない「野良」の状態。投票権は1票に制限されます。
            - `2`: **Verified** (**L2** / Proof of Verification) - CAによって実在確認が行われたが、まだ市民権（L3）としての要件を完全には満たしていない中間状態。投票権は1票のままです。
            - `3`: **Official** (**L3** / Proof of Citizenship) - オーナー事務局まで遡る信頼チェーンを持ち、1台のマシンとして正当な市民権を得た状態。このレベルに達して初めて、15倍（225倍インパクト）の投票権が解放されます。
        - [ ] `social_score` (Integer, NotNull, Default=0): 二次投票(QV)によって蓄積された「熱意の総量」。
            - **定義**: 全世界からそのアプリに対して投じられた「コスト（クレジット）の総額」を意味します。
            - **計算ロジック**: 各投票者が投じた票数($v$)の二乗($v^2$)を合計した値（$\sum v_i^2$）を記録します。これにより、L3市民の「15票」は、「225ポイント」という巨大な熱意として公平に加算されます。
        - [ ] `layer` (Integer, NotNull, Default=0): `verified_level + social_score` の合算値。
            - **役割**: アプリの表示順位（ランキング）を決定するための、単一かつ絶対的な指標です。
            - **運用**: ユーザーノードが勝手に計算するのではなく、CA が責任を持って計算・確定した値を、ユーザーは「キャッシュ」として受け取り保存します。
        - [ ] `votes` (Blob/Binary, Nullable): 投票データの集積体。
            - **構造**: `{ "PubKeyHash": i32 }` の JSON マップを、zstd 圧縮および暗号化したもの。
            - **意図**: 署名検証などの高コストな処理を排除し、「誰が何票入れたか」という事実のみを軽量に保持することで、数百万ノード規模のデータ同期を可能にします。

119. [ ] **DB**: `identities` テーブルへのカラム追加
    - [ ] `verified_level` (Integer, NotNull, Default=0): アイデンティティの信頼ランク。
        - `0`: Unverified
        - `1`: Self-Generated (**L1**) (1票制限)
        - `2`: Verified by CA (**L2**) (1票制限)
        - `3`: Official / Special (**L3**) (投票権拡大: Max 15票)

#### 5.5.2. ビジネスロジック: 信頼の動的導出 (Trust Derivation)
インストール時点での静的な信頼性解析ロジックを実装します。

120. [ ] `apps_bl::determine_verified_level` 関数の実装
    - [ ] 入力: `MyCuteManifest`, 検証済みチェーン情報。
    - [ ] ロジック:
        1. 署名がない -> Level 0.
        2. 署名があり、CAトークンがない -> **Level 1 (Self-Signed / L1)**.
        3. CAトークンがあり、署名検証に成功 -> **Level 2 (Verified / L2)**.
        4. (Option) CAトークンの署名者がOwnerキーと一致 -> **Level 3 (Official / L3)**.
    - [ ] 戻り値: `i32` (0-3).

120-B. [ ] `apps_bl::calculate_layer` ロジックの実装
    - [ ] **責務**: CA ノードが実行する「信頼スコア算出」のコアロジック。この関数こそが、MYCUTE の評価経済の中心エンジンとなります。
    - [ ] **詳細ロジック (The Core Logic)**:
        1.  **データの展開**: 対象アプリの `votes` マップ（PubKeyHash -> 票数）を展開し、メモリー上にロードします。
        2.  **資格の動的確認 (Dynamic Verification)**: 各投票者（PubKeyHash）の現在の `verified_level` を、最新の `identities` テーブルと照合します。
            -   *理由*: 過去に L3 だったユーザーが証明書切れで L2 に降格している場合、その票の重みを即座に剥奪し、現在の身分相応（1票）に戻すためです。
        3.  **票数のクランプ (Clamping)**:
            -   もし現在のランクが L2 以下であれば、投票数がいくら大きくても `1` (または `-1`) に強制変換します。
            -   L3 の場合のみ、最大 `15` までの票数をそのまま認めます。
        4.  **QVスコアの算出 (Quadratic Summation)**:
            -   クランプされた各票数について、その二乗（$v^2$）を計算し、累積加算します（$\sum v_i^2$）。
            -   *意図*: これにより、L3 の 15 票は 225 ポイントとして、L2 の 1 票は 1 ポイントとして集計され、熱意の総量が正しく数値化されます。
        5.  **Layerの確定**:
            -   基礎点である `verified_level` に、算出した `social_score` を加算し、最終的な `layer` 値として確定・保存します。

121. [ ] `apps_bl::install_app_file` の拡張
    - [ ] マニフェスト内の `author` フィールドを抽出し、DBの `author` カラムに保存。
    - [ ] 上記 `determine_verified_level` を実行し、`verified_level` カラムに保存。
    - [ ] **Initial Sync**: インストール完了直後、CA に対して `POST /v1/apps/info` を実行し、最新の `votes` と `social_score` を取得。
    - [ ] 取得したデータを DB に反映する（`layer` 計算はユーザー側では行わず、CA の値を信頼して保存する）。

#### 5.5.3. 実験装置: 二次投票 (QV) システムのコア実装 (Quadratic Logic)
**ルール**: 最上位信頼アイデンティティ (**L3**) のみが「熱意」をコスト ($n^2$) で証明できる。
- **L3のみ**: 最大 $\pm 15$ 票まで投票可能。コストは $votes^2$ (最大 225 クレジット消費)。
- **L2以下**: 最大 $\pm 1$ 票のみ投票可能。コストは 1。

122. [ ] 投票データ構造の定義
    - [ ] **設計思想の変更**: 当初予定していた複雑な署名付き構造体 (`SignedVote`) を廃止し、極限までシンプルなマップ構造を採用します。
    - [ ] **採用構造**: `{ <PubKeyHash>: <投票数(i32)> }` (JSON Map)
    - [ ] **理由と正当性**:
        -   **重複排除**: Map のキーに PubKeyHash を使うことで、同一人物による多重投票は論理的に不可能となります（常に上書きされるため）。
        -   **署名不要**: CA への投稿時に既に本人確認（JWT等）が完了しており、CA が責任を持って検証済みのデータとして DB に格納するため、個別の署名データを持つことは容量の無駄（過剰防衛）と判断しました。
        -   **マージ容易性**: この構造であれば、異なる CA 間のデータ結合も、単純な Map の Merge 操作だけで矛盾なく行えます。

123. [ ] 投票ストレージ `VoteBlob` の読み書きユーティリティ実装
    - [ ] **概要**: `apps` テーブルの `votes` カラム（BLOB）と、Rust の `HashMap` を相互変換するアダプター関数群です。
    - [ ] `read_votes(data: Vec<u8>) -> Result<HashMap<String, i32>>`:
        -   **処理フロー**: 1. システム共有鍵で AES-GCM 復号 -> 2. Zstd アルゴリズムで解凍 -> 3. JSON から HashMap へデシリアライズ。
        -   *目的*: わずかなディスク容量で、数百万件の投票データを効率的に格納・展開するため。
    - [ ] `write_votes(votes: &HashMap) -> Result<Vec<u8>>`:
        -   **処理フロー**: 1. HashMap を JSON 化 -> 2. Zstd で高圧縮 -> 3. システム共有鍵で暗号化。

124. [ ] 投票トランザクション `apps_bl::vote_app` の実装
    - [ ] **Step 1: 資格確認**: `identities` テーブルを参照し、自身の `verified_level` を取得。
    - [ ] **Step 2: 制約チェック**:
        - Level < 3 (L2以下) なら、`abs(votes) > 1` はエラー。
        - Level == 3 (L3) なら、`abs(votes) > 15` はエラー。
    - [ ] **Step 3: データ更新 (Read-Modify-Write)**:
        - DB から現在の `votes` Blob をロード & 復号。
        - 自身の公開鍵ハッシュをキーとして、今回の投票数（i32）を `insert` (上書き)。
        - **注意**: ここでは `layer` の再計算は行わない（次の同期サイクルまたは明示的な再計算リクエストを待つ）。

#### 5.5.4. エコシステム: CAハブと同期サイクル (The Pulse)

125. [ ] **API**: `POST /v1/apps/vote` (投票受付・集約)
    - [ ] **Validator**: CA はリクエスト元の公開鍵を特定し、その権限（L3/L2）に応じた最大票数チェックを行う。
    - [ ] **Effect**: 検証を通過した投票のみを自身の `votes` マップにマージ（PubKeyHashによる重複排除）する。
    - [ ] **構造**: リクエスト自体には署名が必要だが、保管するデータは「検証済みの結果（Hash: Votes）」のみで良い。

126. [ ] **API**: `POST /v1/apps/recalc` (信頼スコア再計算依頼)
    - [ ] **目的**: 開発者が「今すぐ評価を更新してほしい」と CA に依頼するプッシュ型エンドポイント。情報の鮮度を市場競争の武器にします。
    - [ ] **Logic (The Recalc Flow)**:
        1.  **権限確認**: リクエスト送信者が、対象アプリの `author`（所有者）であるか、あるいは一定以上の L3 市民であることを確認します（スパム防止）。
        2.  **計算実行**: バックグラウンドではなく、その場で同期的に `apps_bl::calculate_layer` を実行します。
        3.  **即時反映**: 計算結果（新しい `social_score` と `layer`）を DB にコミットし、レスポンスとして「最新のスコア」を返却します。
    - [ ] **RateLimit**: サーバー負荷を守るため、同一アプリに対する再計算は「1時間に1回まで」等のレートリミットを Redis 等で実装します。

127. [ ] **API**: `GET /v1/ca/status` (CA運用ポリシー公開)
    - [ ] **目的**: その CA がどの程度の頻度で情報を更新しているか（鮮度）や、どのようなポリシーで運営されているかをパブリックに開示するための透明性確保エンドポイントです。
    - [ ] **Response**:
        ```json
        {
            "node_version": "0.1.0",
            "update_policy": "dynamic_market_driven", // 運用方針
            "auto_recalc_interval_sec": 3600,         // 定期再計算の間隔
            "last_calculated_at": 1709251234,         // 最後の全体更新時刻
            "accepts_recalc_request": true           // 開発者からのリクエストを受け付けるか
        }
        ```
    - [ ] **活用**: クライアント（ユーザーアプリ）はこの情報を元に、「活発な CA」を優先的に選択するアルゴリズムを実装できます。

128. [ ] **API**: `POST /v1/apps/info` (カタログ同期)
    - [ ] **Request**: `AppInfoBatchReq { app_ids: Vec<Uuid> }`
    - [ ] **Response**: `AppInfoBatchRes { results: Vec<AppSyncInfo> }`
        - `AppSyncInfo`: `{ id, verified_level, social_score, votes_blob: Option<Vec<u8>> }`
    - [ ] **Logic**: CA は暗号化・圧縮された `votes` ブロブに加え、**計算済みの確定 `layer` 値** を返す。

129. [ ] **Background Task**: 定期同期ロジック (`src/mode/rt/rtevent/sync_task.rs`)
    - [ ] 定期的にターゲット CA に問い合わせ、ローカルの `votes` マップと CA のマップを `extend` でマージする。
    - [ ] これにより、異なる CA 圏の投票も、ユーザーの手元で統合（Union）される。

データと暗号の基盤（本ステージ）が完成した時、MYCUTE は「孤立した完全なノード」となります。
次のステージでは、いよいよこれらのノードを繋ぎ合わせ、巨大な **"OS on OS" P2P Ecosystem** を起動させます。

このステージにおける技術的展望（Technical Roadmap）は以下の通りです。

### 1. Network Layer: Userspace Mesh VPN (EasyTier)
バイナリ単体で機能する **EasyTier** をコアエンジンとして採用し、Tunデバイス（管理者権限）を必要としない **Userspace Networking** を構築します。
- **NAT Traversal**: UDP Hole Punching および TCP Relay による、あらゆるネットワーク環境下での P2P 接続確立。
- **Virtual IP**: `global_app_id` や Identity とは独立した、ネットワーク層でのノード識別子（PeerID）によるルーティング。
- **Embedded Operation**: EasyTier を外部プロセスとしてではなく、Rust ライブラリ（または制御されたサイドカー）として MYCUTE プロセスに統合し、ライフサイクルを完全に管理します。

### 2. Discovery Layer: Gossip Protocol & DHT
「誰がどのアプリを持っているか」という情報を、中央サーバーなしで検索するためのレイヤーです。
- **Catalog Sync (Gossip)**: `identities` テーブルの更新情報や、最新のアプリリリース情報を **Gossipsub** プロトコル（またはそれに準ずるフラッディング）でネットワーク全体に効率的に伝播させます。
- **Content Routing (DHT)**: 特定のアプリ（`global_app_hash`）を保持しているピアを探索するために、**Kademlia DHT** を応用した分散ハッシュテーブルを構築します。これにより、数百万ノード規模でも O(log N) でソースノードを特定できます。

### 3. Transport Layer: Content Addressable Transfer
ファイル転送は、単なるサーバー・クライアント間のダウンロードではなく、BitTorrent や IPFS のような **Content Addressable** な仕組みに進化します。
- **Merkle DAG**: `.mycute` パッケージをチャンク分割し、それぞれのハッシュを検証しながら並列ダウンロードします。
- **Source Agnostic**: データは「特定のサーバー」からではなく、「そのハッシュを持つ最も近い複数のノード」から取得されます。
- **Resumable & Deduplication**: `global_app_hash` が一致する限り、同じデータの再ダウンロードは発生しません。

### 4. Trust Layer: Web of Trust with CA
本ステージ（Phase 2）で実装する `identities` テーブルと Ed448 署名基盤が、ここで真価を発揮します。
- **On-chain Like Verification**: アプリの署名検証は、ノードが自律的に行います。CA の役割は「署名を発行すること」だけであり、通信の仲介は一切行いません。
- **Reputation System**: 将来的には、CA 認証だけでなく、ユーザー間の直接的な信頼関係（Web of Trust）を `identities` テーブルに拡張記録することも可能です。

**全ては、本ステージで構築する「堅牢なデータスキーマ」と「暗号学的アイデンティティ」の上に築かれます。**
データ構造に矛盾がない限り、ネットワーク層はどのようにでも拡張可能です。我々は今、そのための揺るぎない礎石を置いているのです。
