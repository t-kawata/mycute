やりたいことを実現するには、ざっくり言うと次の2段階があります。

1. **「壊れている」ダイアログをなくす**  
2. その代わりに「未確認の開発元だけど開く？」レベルのダイアログにする  

macOS 的には、これを実現するための現実的なラインが次の3パターンです。

***

## 選択肢の全体像

- パターン A: 開発者署名 + notarization（Apple Developer アカウント必須・推奨）  
- パターン B: ad-hoc 署名のみ（Apple アカウント不要・ただし「未確認の開発元」扱い）  
- パターン C: ユーザー側の Gatekeeper 設定に依存（`spctl --master-disable` など）  

「“壊れているため開けません”」を避けて、「未確認の開発元ですが開きますか？」にしたいなら、**最低でも B（ad-hoc 署名）**、理想は **A（Developer ID 署名 + notarization）** です。 [eclecticlight](https://eclecticlight.co/2023/07/05/how-does-ventura-check-the-security-of-known-apps-and-command-tools/)

***

## パターン A: Developer ID 署名 + Notarization（本命）

Apple の Developer ID で署名 & notarization すると、配布先での UX はかなり素直になります。 [stackoverflow](https://stackoverflow.com/questions/78297082/code-signing-a-tauri-application-on-windows-and-macos)

- 初回起動時の挙動はだいたい次のようになる:
  - ダイアログは出るが、「Apple によって確認済み」扱いになり、ユーザーはそのまま「開く」ボタンを押すだけでよい（OSバージョンによって文言は多少変わる）。 [support.apple](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac)
- 以降は普通のアプリ同様に起動可能。

Tauri 側のセットアップとしては、ざっくり:

1. Apple Developer アカウントで **Developer ID Application** 証明書を作成してキーチェーンに入れる。 [v2.tauri](https://v2.tauri.app/distribute/sign/macos/)
2. `APPLE_SIGNING_IDENTITY`, `APPLE_TEAM_ID` などを環境変数で設定。 [tauri](https://tauri.app/v1/guides/distribution/sign-macos)
3. notarization 用に App Store Connect API キー or Apple ID + app-specific password を設定。 [dev](https://dev.to/tomtomdu73/ship-your-tauri-v2-app-like-a-pro-code-signing-for-macos-and-windows-part-12-3o9n)
4. `tauri build` 実行時に Tauri が自動で  
   - バイナリを署名  
   - Apple にアップロードして notarization  
   - チケットを stapling  
   までやってくれる構成にする。 [tauri](https://tauri.app/v1/guides/distribution/sign-macos)

参考:  
- Tauri v2 docs: macOS Code Signing。 [v2.tauri](https://v2.tauri.app/distribute/sign/macos/)
- Tauri + notarization まとめ記事（日本語）。 [dev.classmethod](https://dev.classmethod.jp/articles/shuntaka-tauri-macos-codesign-notarization-updater-github-releases/)

これは年間 99 USD の有料 Developer アカウントが前提ですが、**ユーザーにターミナル操作をさせず配布したい**なら、基本的にはこのルート一択に近いです。

***

## パターン B: ad-hoc 署名だけ行う（無料）

Apple の Developer ID は使わず、`codesign` で ad-hoc 署名（`-` identity）をしておくやり方です。 [eclecticlight](https://eclecticlight.co/2023/07/05/how-does-ventura-check-the-security-of-known-apps-and-command-tools/)

- 特徴:
  - 実物の開発者証明書は不要。
  - ただし notarization がないので、初回は Gatekeeper によるブロックが入る可能性が高い。 [eclecticlight](https://eclecticlight.co/2023/07/05/how-does-ventura-check-the-security-of-known-apps-and-command-tools/)
  - その場合でも、ユーザーは
    - Finder で右クリック → 「開く」  
    - または「システム設定 → プライバシーとセキュリティ → “このアプリはブロックされました” → “許可”」  
    を踏めば起動を許可できる。 [support.bemopro](https://support.bemopro.com/hc/en-us/articles/42102299641363-How-to-Allow-Apps-from-Unidentified-Developers-on-macOS)

Tauri のバンドル後に、CI かローカルで:

```bash
codesign --force --deep --sign - /path/to/mycute.app
```

のように ad-hoc 署名してから配布する形です。 [eclecticlight](https://eclecticlight.co/2023/07/05/how-does-ventura-check-the-security-of-known-apps-and-command-tools/)

これでも「壊れているため開けません」が「未確認の開発元なので開けません」寄りのメッセージに変わるケースが多く、ユーザーは GUI 上で「開く」を選ばせることができます。 [support.apple](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac)

***

## パターン C: ユーザーの Gatekeeper を弱める（おすすめ度低）

ユーザーに

- システム設定の「App Store と確認済みの開発元」設定を緩めてもらう  
- あるいは `sudo spctl --master-disable` で「どこからでも許可」を有効にしてもらう [macworld](https://www.macworld.com/article/672947/how-to-open-a-mac-app-from-an-unidentified-developer.html)

という方法もありますが、

- セキュリティを全体的に下げる  
- macOS バージョンによって挙動が変わる  
- プロダクトの配布 UX としてはイマイチ  

なので、「自分の開発マシン専用」以外にはあまり勧めづらいです。 [macworld](https://www.macworld.com/article/672947/how-to-open-a-mac-app-from-an-unidentified-developer.html)

***

## 今の目的に対するおすすめ

- 「せめて“未確認の開発元だけど実行していい？”レベルにしたい」  
- 「一般ユーザーに xattr を叩かせたくない」

という条件だと、

- **本気の配布 = パターン A: Developer ID 署名 + notarization**  
- **ひとまず身内配布/テスト = パターン B: ad-hoc 署名**  

のどちらかを取るのが現実解です。 [dev.classmethod](https://dev.classmethod.jp/articles/shuntaka-tauri-macos-codesign-notarization-updater-github-releases/)
