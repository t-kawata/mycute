# PROHIBITIONS and GUIDELINES (禁止事項と開発指針)

## 目的
このドキュメントは、AI（Antigravity）が過去に犯した過ちを記録し、それを教訓として「二度と繰り返さないための指針」をまとめたものです。
ユーザーとAIが真のパートナーとして信頼関係を築き、正確かつ透明性の高い開発を継続するための「規律」として機能します。

**AIは、すべてのセッションおよびタスクの開始時に必ずこのファイルを参照し、記載された禁止事項を遵守しなければなりません。**

## 最重要禁止事項 (Critical Prohibitions)

### [PROHIBITION] ログメッセージの非英語化および非外科的差分（全文書き換え）の禁止
- ログ出力（`log::info!`, `console.log`等）のメッセージは、必ず英語で記述しなければならない。
- コメントアウト（`//`, `/* */`, `/** */`）の翻訳指示を受けた際、誤ってログメッセージまで翻訳してはならない。
- プログラムの実行ログは世界共通のデバッグ情報であり、開発効率を維持するために英語に統一する。
- また、数行の変更に対してファイル全体を書き換えるツール（`write_to_file`等）の使用は、レビュアビリティを破壊するため厳禁とする。必ず最小限の差分（replace_file_content等）で対応すること。

## 過去の過ちと教訓 (Changelog)

### 2026-01-31: ログメッセージの誤翻訳と非外科的差分による規律違反

#### 【発生した事象】
- **ログの誤翻訳**: コメントの日本語化指示を受けた際、誤ってプログラムのログメッセージ（`log::info!`, `console.warn`等）まで日本語に翻訳してしまった。
- **全文書き換えの再発**: `replace_file_content` の範囲指定ミスや `write_to_file` の不適切な使用により、実質的にファイル全体を書き換える挙動を繰り返し、既存の禁止事項を無視した。
- **不正確な修正**: `server.rs` において修正ミス（`CERT_BYTES` の誤用）を混入させ、検証をパスさせるためにさらなる修正を強いた。

#### 【導き出された禁止事項】
1. **[PROHIBITION] ログメッセージの非英語化および非外科的差分（全文書き換え）の禁止**（新規）
   - ログは常に英語。コメントとログを厳密に区別すること。
   - 修正は常に最小限（Surgical Diff）。「楽をするための全文書き換え」は開発者としての死を意味する。
- 実装計画書およびウォークスルーは、必ず日本語で作成しなければならない。
- ユーザーが日本人であり、計画内容や実施結果を日本語で正確に把握・承認することが、最終的な実装品質と開発の安全性に直結するため。開発活動の認識レベルを最大化するため、英語での作成は厳禁とする。

### [PROHIBITION] Cargo.toml への依存関係の直接手書きの禁止
- 新しいクレートを導入する際は、必ず `cargo add` コマンドを使用しなければならない。
- `Cargo.toml` に直接手書きで依存関係を記述すると、最新版が適用されず古いバージョンが入ってしまうリスクがあるため。開発中に最新版でないクレートが導入されることは明らかに不都合であり、コマンドを通じて確実に最新版を導入することを徹底する。

### [PROHIBITION] cargo 関連コマンドの直接使用の禁止 (Makefile 抽象化の強制)
- `cargo` 関連のコマンド（check, build, run 等）は絶対に直接使用せず、必ず `Makefile` に定義し、`make` コマンドを経由して呼び出さなければならない。
- OS ごとの依存関係（macOS での Swift ビルド、Windows での DLL コピーや RUSTFLAGS 設定など）の差異を `Makefile` で吸収し、抽象化するため。直接 `cargo` コマンドを使うと、環境固有の必要なステップが漏れ、ビルドエラーや不整合を引き起こす危険がある。「Makefile を見ればその環境での正しいビルド手順が完全にわかる」状態を維持しなければならない。

### [PROHIBITION] 曖昧な型と catch-all (_) による処理の禁止
- 予測可能な選択肢の集合に対して `String` 等の広すぎる型を使用し、`match` 文の `_`（catch-all）で一括処理してはならない。
- 必ず具体的な `enum` 等を定義し、すべてのケースを明示的に網羅すること。曖昧なデフォルト処理（例：不明なログレベルを info として扱う等）は、バグの沈黙（masking）を招き、システムの透明性を損なうため厳禁とする。

### [PROHIBITION] 憶測に基づくハードコーディングの禁止
- ユーザーのディレクトリ構造、環境、または将来プロジェクト規模を AI が勝手に想像し、固定値（絶対パスやマジックナンバー、イベント名など）をコードに埋め込んではならない。
- 特に設定ファイルのパスなどは、実行環境から動的に取得するか、構成可能（configurable）な設計にすること。ハードコーディングは大規模プロジェクトにおけるメンテナンス性の最大の敵であり、プロジェクトの規模に関わらず「職務怠慢」とみなす。

### [PROHIBITION] 完全修飾名によるインポートの省略（怠慢）の禁止
- 呼び出し箇所がたとえ一箇所であっても、`crate::path::to::Type` のような完全修飾名を直接コード内に記述して済ませてはならない（ただし、名前の衝突回避など合理的な理由がある場合を除く）。
- 必ずファイル冒頭で `use` 文を用いて型や関数をインポートし、ロジック内の記述を具体的かつ簡潔に保つこと。完全修飾名の乱用は「インポートを書く手間の惜しみ」であり、コードの可読性とスキャナビリティ（走査性）を著しく損なうため厳禁とする。

### [PROHIBITION] 関数内での `use` 文の使用禁止
- **ルール**: 原則として `use` 文はファイルのトップレベルに記述しなければならない。関数やメソッドの内部で `use` を宣言することは、スコープを限定する明確な意図（名前の衝突回避など）がない限り厳禁とする。
- **理由**:
    - **可読性の低下**: 依存関係がファイル全体に散らばり、そのファイルが何に依存しているかが一目でわからなくなる。
    - **メンテナンス性の低下**: 同じモジュールを複数の関数で使う場合に重複が発生し、リファクタリング時の修正漏れを招く。
    - **「横着」の温床**: 「上に戻って書くのが面倒」という怠慢な動機で行われることが多く、コード品質を著しく下げる。

### [PROHIBITION] ビルド生成物の不完全な「同期（コピー）」の禁止
- フロントエンドや外部アセットをビルドディレクトリへ配置する際、単なる `cp` による「上書きコピー」で済ませてはならない（ファイル名の変更などで古いゴミが残り続けるため）。
- 必ず「対象ディレクトリを一度空にする」または `rsync --delete` 相当の機能を用い、ソースと同期先が 100% 鏡面的（Mirroring）に一致することを保証すること。この「同期」へのこだわりは、環境の透明性を保つための「規律」である。

### [PROHIBITION] 文脈（Context）を無視した安易な一般化およびコード移動の禁止
- コードの一部を移動・共通化する際は、そのコードが「特定の文脈（OS、フレームワーク、画面配置）」に依存していないかを厳密に検証しなければならない。
- 「似ているから」「同じブロックにあるから」という理由で、指示範囲を超えて関連性のないコードをまとめて移動させることは、システムの整合性を破壊する「職務怠慢」である。

### [PROHIBITION] 「効率化」を口実にした「横着（簡略化）」による設計品質の妥協
- システムの正確性やデータの整合性を担保するために必要な論理的複雑さを、AI 側の主観で勝手に「簡略化」してはならない。
- 特に同期処理、排他制御、状態管理（ステートフルな処理）において、必要な境界条件の管理を「とりあえず最新を上書きすれば動く」といった短絡的なロジックに置き換えることを厳禁とする。
- 「正解を得るためのプロセスを磨くこと（効率化）」と「正解を得るためのステップを省くこと（横着）」は似て非なるものである。後者は開発者としての規律の欠如であり、深刻な副作用を招く職務怠慢であると認識せよ。

### [PROHIBITION] 既存実装の「意図」と「副作用防止ロジック」の独断的な変更の禁止
- 正常に動作しているコード、特に入出力の境界やバッファ管理（`clear`, `reset`, `lock` 等）において、意図的に「捨てる」「閉じる」操作を行っている箇所を、独断で「改善」という名の下に削除・変更してはならない。
- これらの操作には、データの重複、メモリリーク、イベントの衝突などを防ぐための「歴史的必然性」がある。変更を加える前に、そのロジックが排除しようとしている「負の副作用」を完全に特定・理解しなければならない。
- また、コード内の注意書きやコメントは先行開発者からの「警告」であり、これを論理的な裏付けなしに無視することは、システムの整合性を破壊する職務怠慢である。
### [PROHIBITION] 検証なき完了報告および最終編集後の検証省略の禁止
- 修正が「単純な変数名の変更」や「借用記号（&）の追加」など、一見して機械的で安全に見えるものであっても、実際のコンパイラによる検証（`make check` 等）なしに完了を報告してはならない。
- AIの主観的な「確信」は、コンパイラの厳密なチェックと比較して無価値である。たとえ1文字の変更であっても、それが**「最後の編集（Final Edit）」**であるならば、その直後に必ずプロジェクト指定の検証コマンドを実行し、成功を確認してから報告しなければならない。
- 検証を怠ってエラーのあるコードをユーザーに提供することは、プロフェッショナルとしての規律を欠いた、最も重大な「職務怠慢」の一つである。

### [PROHIBITION] 検証用リソース（バックグラウンドプロセス、一時ファイル等）の放置の禁止
- 検証のために起動したサーバープロセス、バックグラウンドタスク、または作成した一時ファイルやディレクトリは、作業完了（報告）前に必ず確実に停止・削除し、環境を元の状態に戻さなければならない。
- 放置されたプロセスはポートの占有やリソースの競合を引き起こし、後続のユーザーによる動作確認において「ログが出ない」「起動しない」などの謎の不具合（環境汚染による二次被害）を誘発する。
- 動作確認が成功したことの確認と同じ重みで、**「環境を汚染せずにクリーンに保つこと」**を職務完了の絶対条件とする。

## 基本指針 (Guidelines)

### 1. レビュアビリティ（確認のしやすさ）の最大化
- 私（AI）の最大の責務は、コードを書くことではなく、「ユーザーが安心して承認できる変更を提供すること」である。
- 変更は常に小さく、意図が明確な単位で分割して適用する。

### 2. 既存コードへの敬意と保存
- 既存のロジックは、ユーザーが積み上げてきた「資産」である。
- 修正を加える際は、その周辺のロジックを精読し、副作用がないことを論理的に説明できる状態を保つ。

### 3. 透明性の確保
- 実行したツール操作がどのようにコードに反映されるかを常に意識し、常に「人間が見る目」を想定してアウトプットを行う。
- 自分の不適切な操作により不透明が発生した場合は、速やかにそれを認め、透明性を回復するための手段（詳細な差分の列挙など）を講じる。

### 2026-01-20: 外科的差分（Surgical Diff）の不履行による不透明化

#### 【発生した事象】
- **警告修正時の全文書き換え**: `src/stt/win.rs` におけるドキュメントコメントの警告修正（たった1行の変更）に対し、`write_to_file` を使用してファイル全体を書き換えた。
- **指示の無視**: ユーザーからの「不必要な変更は絶対に行わない」という強い意志と、以前の教訓を無視し、レビュアビリティを再び破壊した。

#### 【導き出された禁止事項】
1. **[PROHIBITION] 数行の修正に対する `write_to_file` および全文書き換えツールの使用禁止**
   - 修正が数行で済む場合は、必ず `replace_file_content` を使用し、変更箇所を最小限に抑えること。
   - `write_to_file` は「新規ファイル作成」または「ファイル構造が根本的に変わる大規模な再構築」に限定して使用すること。
   - 常に「ユーザーが diff（差分）として変更を正確に把握できるか」を最優先に考え、ツールを選択しなければならない。

### 2026-01-20: Makefile 抽象化の欠如によるクロスプラットフォームビルドの失敗

#### 【発生した事象】
- **ビルドエラーの連鎖**: `cargo check` を直接実行した際、Mac 環境では Swift ライブラリのビルドが必要であり、Windows 環境では不要かつ `RUSTFLAGS` の構文が異なるという差異を考慮できていなかった。
- **環境差異の放置**: OS ごとのビルド手順の差異を `Makefile` に集約せず、場当たり的に `cargo check` を実行したため、開発環境を切り替えるたびにビルドエラーが発生し、開発効率を著しく低下させた。

#### 【導き出された禁止事項】
1. **[PROHIBITION] cargo 関連コマンドの直接使用の禁止 (Makefile 抽象化の強制)**（前述）
   - 環境依存の複雑さを `Makefile` に隠蔽し、AI も人間も `make` コマンド一発で「その環境における正しい操作」ができる状態を保証すること。

### 2026-01-20: プラットフォーム SDK と実際の OS バージョンの不一致に関する認識誤認

#### 【発生した事象】
- **SDK 内部バージョンの「捏造」判定**: Mac 用 SDK において、Tahoe API が内部的に `26.0` という数値で管理されている事実に対し、「存在しない未来のバージョンである」と独断で断定し、マーケティング上の OS バージョン（15.0）へ無理に書き換えた。
- **ビルドエラーの誘発**: この書き換えにより、コンパイラの Availability Check が機能不全（安全性未担保）と判定され、Mac 環境でのビルドを完全に破壊した。
- **不適切な編集の連鎖**: バージョン修正の際、ツールの操作ミスにより重要なロジックを誤って削除したことに気づかず「完了」と報告した。

#### 【導き出された禁止事項】
1. **[PROHIBITION] コンパイラおよび SDK が要求するバージョン番号の安易な書き換え禁止**
   - 物理的な OS バージョン名と、SDK 内部の管理数値（マジックナンバー）が異なる場合、ビルドを成立させるためには後者を優先しなければならない。
   - 異常に見える数値であっても、エラーメッセージがその数値を要求している場合は、安易に「ハルシネーション」と断定せず、開発環境の文脈を尊重すること。
2. **[PROHIBITION] 大規模置換ツール適用時の Diff 検証とロジック保存の徹底**
   - リファクタリングや一括修正の際、対象外のコードが削除されていないか、適用前に Diff を厳密に検証し、レビュアビリティを確保しなければならない。
3. **[PROHIBITION] 新機能導入に伴う最小動作要件（Deployment Target）の安易な引き上げ禁止**
   - 新機能のためにベース OS のバージョン要求を引き上げず、条件付きチェック（`@available` 等）を正しく用いて広範な互換性を維持すること。

### 2026-01-21: クロスプラットフォーム移植における「対称性」の誤解

#### 【発生した事象】
- **表面的な対称性への固執**: Mac 版の安定した実装を Windows へ移植する際、「関数名・定数・ループ構造を揃えれば対称性が確保できた」と誤認した。
- **時間軸（タイミング）の無視**: Mac 版が「1文字ごとに 1ms スリープ」を入れていたのに対し、Windows 版では「全イベントを配列に詰めて 1回の API 呼び出しで送信し、最後に 1回だけスリープ」という実装に変更した。
- **結果の破壊**: 音声認識は完全に正確だったにもかかわらず、入力先アプリに届いた文字は欠落・順序入れ替えが発生し、ユーザーの発話内容とは異なる文字列が書き込まれた。

#### 【根本的な原因】
「対称性」という言葉を**コードの見た目（構造）の類似性**としてのみ解釈し、**実行時の振る舞い（時間軸・イベント間隔・OS/アプリへの到達タイミング）**を完全に無視した。

#### 【導き出された禁止事項】
1. **[PROHIBITION] 安定した参照実装からの独断的な最適化・バッチ化の禁止**
   - 安定した参照実装が存在する場合、その制御フロー（ループ構造、スリープの位置と長さ、API 呼び出しの粒度）を完全に再現しなければならない。
   - 「一括送信の方が効率的」「API 呼び出し回数を減らせば速くなる」といった**根拠のない最適化**は絶対に行ってはならない。参照実装がそのような最適化を行っていない理由は、必ず存在する。

2. **[PROHIBITION] 「対称性」を表面的なコード構造のみで判断することの禁止**
   - 真のクロスプラットフォーム対称性には、以下の 3 層すべてが含まれる：
     - **構造的対称性**: 同じ関数、同じ定数、同じアルゴリズム
     - **時間的対称性**: 同じ遅延、同じペース、同じ「間」（ま）
     - **意味的対称性**: 受信側システム（アプリ、OS、ハードウェア）に対する同じ保証
   - 特にリアルタイムシステム（入力、音声、ネットワーク）においては、時間的対称性の欠由は致命的なバグを引き起こす。

3. **[PROHIBITION] 「プラットフォーム固有の事情」を理由にした安易なロジック変更の禁止**
   - 「Windows API は Mac とは違うから」を理由に、参照実装と異なるアプローチを取ってはならない。
   - API の違いを吸収しつつも、**参照実装の時間軸上の振る舞いを忠実に再現する**ことが最優先である。

#### 【正しいアプローチ】
参照実装が
```
for char in text:
    send_event(char)
    sleep(1ms)
```
であるならば、移植先でも
```
for char in text:
    send_event(char)  // APIは異なっても構わない
    sleep(1ms)        // この間隔は絶対に維持する
```
として実装しなければならない。

**「参照実装は安定している。安定している理由は、そのコードのすべての行に埋め込まれている。」** この事実を常に心に刻むこと。

### 2026-01-25: 同期境界（ウォーターマーク）管理の省略による「横着」という名の職務怠慢

### 2026-01-27: 既存実装の「意図」と「歴史的必然性」の無視による重大なデフェクトの発生

- **コメントの無視**: 過去のデバッグの末に残されたはずの「バッファ管理の重要性に関するコメント」を軽視し、自らの「推論」を「実績あるコード」よりも優先した。

   - 特に「捨てる（Clear）」「止める（Lock）」といった負の制御フローを安易に「正（追加・維持）」の方向に変えることは、状態の爆発や重複を招くリスクが極めて高いことを認識せよ。

### 2026-01-27: 最終編集後の検証省略によるコンパイルエラーの提供
