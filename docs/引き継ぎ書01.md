# MYCUTE 通信アーキテクチャ 抜本的移行計画書 (Protocol to Domain Suffix)

## 1. 概要と背景
本ドキュメントは、MYCUTE プロジェクトにおける通信基盤の設計変更（独自プロトコルからドメイン・サフィックス方式への移行）に関する全てのコンテキストと技術詳細をまとめたものである。

MYCUTE は、既存の Web サイトに SDK を自動注入し、Service Worker (SW) を介して全ての通信を制御・加工することを目指している。当初は `mycutes://` という独自プロトコルを定義し、それを「安全なコンテキスト」として OS (WebKit) に認識させる戦略をとったが、Apple の強固な文字列レベルのチェック（`http/https` 以外の排斥）に阻まれ、SW の動作が完全に封殺される結果となった。

この課題を根本から解決するため、プロトコルは標準の `https://` を維持したまま、ドメインの末尾に特殊な識別子（サフィックス）を付与することでプロキシを通す「Domain Suffix Proxy 方式」へと移行を決定した。

---

## 2. WebKit との闘争の歴史と検証結果
これまで実施した試行錯誤の詳細は以下の通りである。これを知ることで、なぜ「サフィックス方式」が唯一の生存戦略であるかが理解できる。

### 2.1. ネイティブ FFI による介入 (Swift 実装)
*   **実施内容**: `native/swift/ProtocolHelper.swift` を作成し、WebKit のプライベート API (`_registerURLSchemeAsSecure:`, `_registerURLSchemeAsServiceWorkerAllowed:` 等) を呼び出した。
*   **検証タイミング**: Tauri の `setup` フック内、および `main` 関数の冒頭。
*   **結果**: WebKit 内部の「スキーム登録レジストリ」には登録され、CORS やセキュリティ制限は一部緩和されたが、JavaScript API 層 (`serviceWorker.register`) の呼び出し時に `TypeError: protocol must be http or https` が発生。
*   **結論**: WebKit の JS バインディング層には、セキュリティ属性のチェック**以前に**、文字列が "http" か "https" であるかをリテラルで判定して例外を投げるコードがハードコードされている。ネイティブ層からの介入では、この JS 層の壁を越えることはできない。

### 2.2. Service Worker のプロトコル要件
Service Worker は W3C 仕様により「Secure Context」かつ「HTTP/HTTPS スキーム」であることが厳格に求められる。独自スキーム (`mycutes://`) を使う限り、ブラウザエンジンを魔改造しない限りはこの制限を回避できない。

## 3. 新設計：Domain Suffix Proxy 方式の全容

### 3.1. 基本ルール
*   **URL の変遷**:
    *   オリジン: `https://example.com`
    *   MYCUTE 経由: `https://example.com.mc.local`
*   **識別子 (Suffix)**: `.mc.local` (定数名: `MYCUTE_PROXY_SUFFIX`)
*   **メリット**:
    1.  **SW の完全動作**: ブラウザからは「標準の HTTPS」に見えるため、SW が 100% 動作する。
    2.  **OS 非依存**: Windows (WebView2) も Mac (WebKit) も、標準プロキシとして振る舞うだけで対応可能。
    3.  **セキュリティ**: HTTPS プロトコルを維持するため、既存の Web セキュリティモデルと親和性が高い。

## 4. 各コンポーネントの具体的改修内容

### 4.1. Rust コア層 (Proxy Handler)
現在 `src/myproxy/` で実装されているプロキシ・ハンドラを、スキーム判定からドメイン判定へ切り替える。

1.  **判定ロジック**: `req.uri().host()` が `.mc.local` で終わっているかをチェック。
2.  **ドメイン変換**:
    *   リクエスト時: `google.com.mc.local` → `google.com` (Host ヘッダーの書き換え必須)。
    *   レスポンス時: レスポンスボディ内の URL や、`Location` ヘッダー内の URL を検知し、自動的に `.mc.local` を付与してブラウザに返す（透過プロキシ）。
3.  **CORS 制御**: プロキシ先からの CORS ヘッダーを適切に書き換え、ブラウザが「同一オリジン」または「許可されたクロスオリジン」として認識するように制御する。

### 4.2. SDK (TypeScript) 層
`sdk-ts/` 内の URL 変換およびインターセプター群を抜本的に改修する。本プロジェクトにおいて最も複雑なパートである。

1.  **URL 改竄エンジン (`url.ts`)**:
    *   `toMycuteUrl(url)` 関数を、スキームの置換ではなく、ホスト名へのサフィックス付与に変更。
    *   `fromMycuteUrl(url)` 関数で、サフィックスを除去して本来の URL を復元。
2.  **DOM インターセプター (MutationObserver)**:
    *   `<a>` タグの `href`、`<iframe>` の `src`、`<form>` の `action` などを動的に書き換える。
    *   例: `<a href="https://example.com">` → `<a href="https://example.com.mc.local">`
3.  **API インターセプター (Fetch / XHR)**:
    *   JS 空間で発行されるすべてのリクエストをトラップし、宛先 URL にサフィックスが付いていない場合は自動付与する。
4.  **Service Worker 連携**:
    *   SW 登録時の URL を `https://...` 形式で維持。
    *   SW 内で発生する `fetch` イベントに対しても、サフィックス付与ロジックを適用する。
5.  **Cookie ハンドリング**:
    *   `.mc.local` というドメイン空間で Cookie が維持されるように、`set-cookie` ヘッダーの `Domain` 属性をプロキシ側で適切に調整する。

### 4.3. 定数の統合管理 (`src/constants.rs`)
不整合を防ぐため、「唯一の真実」である `constants.rs` を更新する。

1.  `pub const MYCUTE_PROXY_SUFFIX: &str = ".mc.local";` を追加。
2.  `make build-sdk-ts` を実行し、`sdk-ts/src/generated_constants.ts` へ自動反映させる。

## 5. 技術的課題と解決プラン

### 5.1. 名前解決 (DNS) の壁
ブラウザが `example.com.mc.local` を解決しようとした際、それが Rust のローカルプロキシ（`127.0.0.1`）に向かなくてはならない。

*   **解決案 A**: Tauri の `additional_browser_args` にて、`--proxy-server=http://127.0.0.1:PORT` を指定し、全トラフィックを奪う。
*   **解決案 B**: 本物の DNS を汚染せず、Tauri (Custom Protocol ハンドラ) を使って特定のドメインパターンのみを横取りする設定が可能か検証。
*   **現在の推奨**: WebView2/WebKit ともに、アプリケーションレベルでのプロキシ設定を併用するのが最も確実。

### 5.2. 証明書 (SSL/TLS) の壁
`https://...` を維持する場合、証明書のエラーが表示される可能性がある。

*   **解決案**: Tauri 内部でリッスンするプロキシサーバーに自己署名証明書を持たせるか、あるいは `ignore-certificate-errors` フラグを立てる（開発・内部利用と割り切る）。
    *   **★最重要**: ターゲットとなる WebView 側のセキュリティ設定を、これらの `.local` ドメインに対しても緩和する設定が必要。

## 6. 実装ロードマップ（次セッションの作業手順）

1.  **Phase 1: 環境整備**
    *   `constants.rs` にサフィックスを定義。
    *   `native/swift/` 下の古いプロトコル登録関連コードを「勇気を持って」削除または無効化。
2.  **Phase 2: SDK 定義変更**
    *   `sdk-ts` の URL 変換ロジックをサフィックス方式に変更してビルド。
3.  **Phase 3: プロキシロジック刷新**
    *   Rust 側のスキームベースの判定を、ドメインサフィックスベースに変更。
    *   ホスト書き換え処理の実装。
4.  **Phase 4: 動作検証**
    *   サフィックス付き URL で SW が `TypeError` を出さずに登録されるかを確認。
    *   CORS が崩壊していないかをチェック。
