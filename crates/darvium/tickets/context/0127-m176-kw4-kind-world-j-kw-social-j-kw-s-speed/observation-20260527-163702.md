## 3. 較正ループ

### 反復 1（Cycle 1: 初期探索）
- 仮説: lambda_gc_base を [0.1, 0.5] に狭窄し、gamma_benevolence を 0.60 に増加すると GC 死亡が減少する
- 変更定数: KW4_SIMULATION_TICKS(100→200), KW4_CONVERGENCE_THRESHOLD(0.8→0.1), KW4_INITIAL_GAMMA_BENEVOLENCE(0.30→0.60), KW4_EVALUATION_POPULATION_SIZE(50→200), KW4_LAMBDA_GC_BASE_RANGE([0.1,2.0]→[0.1,0.5]), KW4_GAMMA_BENEVOLENCE_RANGE([0.0,0.8]→[0.0,1.0])
- 観測結果: J_kw_social=0.028, j_child_survival=0.0
- 解釈: 子供の lifecycle_score=0（usage=0 による幾何平均 0）により gamma_lifecycle 項が無効化。gamma_child_protect が唯一の防御だが 0.20 では不十分。

### 反復 2（Cycle 2: 範囲狭窄）
- 仮説: gamma_child_protect を 4 倍にし child_ratio を減らし population を増やす
- 変更定数: GC_HAZARD_GAMMA_CHILD_PROTECT(0.20→0.80), KW4_CHILD_RATIO_RANGE([0.1,0.5]→[0.05,0.25]), KW4_EVALUATION_POPULATION_SIZE(200→400)
- 観測結果: J_kw_social=0.030, j_child_survival=0.0（依然として 0 で不可解）
- 解釈: 理論上の生存率 ≈ 87%/3checks だが実際は 0%。推移関数または生存確率計算に問題がある可能性。

### 反復 3（Cycle 2b: 子保護極限強化）
- 仮説: gamma_child_protect=10.0 で inner ≈ -5.19 → softplus ≈ 0.0002 → survival > 99.9%/check
- 変更定数: GC_HAZARD_GAMMA_CHILD_PROTECT(0.80→10.0)
- 観測結果: J_kw_social=0.053, j_child_survival=0.92, j_help=0.0（依然）
- 解釈: 子保護は成功。しかし help_success_rate が 0 で j_help が効かない。

### 反復 4（Cycle 3: HELP 計測修正）
- 仮説: help_success_rate が ctx.help_sessions（完了セッション削除済）を使用しているため常に 0。累積カウンタに修正。
- 変更定数: GC_HAZARD_GAMMA_CHILD_PROTECT(0.80→10.0)継続 + help_success_rate 計算式修正
- 観測結果: J_kw_social=0.061, j_help=0.40, j_child_survival=1.0, converged=false
- 解釈: HELP 計測は有効化されたが、j_reciprocity=0.0 が常時で s_topology に硬天井 ≈ 0.48。J_kw_social の最大到達値 ≈ 0.06。

## 4. 現象の解釈

外側ループ 3 サイクルの較正により、以下の構造的制約が明らかになった：

1. **子ノードの脆弱性**: children は experience=0 のため lifecycle_score が常に 0（幾何平均の性質で usage=0 → 全体 0）。これにより gamma_lifecycle 項が機能せず、gamma_child_protect が唯一の防御機構となる。結果として gamma_child_protect は 0.20 では不十分で、10.0 という非現実的な高値が必要。

2. **HELP プロトコル計測の不具合**: help_success_rate は ctx.help_sessions から計算されていたが、このリストはシミュレーションループ内で完了セッションを削除するため、最終 tick では常に空または数件のみ。累積カウンタ（total_help_attempts/total_help_successes）を使用する修正が必要だった。

3. **J_kw_social の硬天井**: 現在のシミュレーション構造では j_reciprocity=0（互恵性相互作用が発生しない設計）、j_reuse=0（ワークフロー再利用が発生しない）という制約により、s_topology と s_search が低く抑えられる。理論的最大 J_kw_social ≈ 0.20、実際の到達値 ≈ 0.06。

4. **収束しない Nelder-Mead**: 目的関数のランドスケープが平坦（多くのパラメータ組合せで 0.050-0.061 の狭い範囲に収束）なため、200 iteration 後も収束しなかった。これは目的関数に有益な勾配が不足していることを示す。

## 5. 目的関数 J(θ) の評価

- **収束速度**: s_speed=0.95（ttc=10 tick）— 非常に速いが、これは閾値 0.1 が低すぎて最初のサンプリング時点で常に超過するため。「真の収束」ではなく「低品質平衡への早期到達」
- **定常誤差**: J_kw_social=0.061（目標 0.64 の 9.5%）— 構造的制約により大幅な改善は困難
- **オーバーシュート**: なし（単調増加的な評価値）
- **総合評価**: 内側ループ（Nelder-Mead）は所定の探索範囲内で最適化を完了したが、目的関数自体が構造的ボトルネックの影響を受けて低い値に留まった。Kind World 条件（J_kw_social > 0.64 ∧ min(s_i) > 0.6）は現在のシミュレーション構造では達成不可能。

## 6. 次チケットへの示唆

1. **j_child_survival 問題の抜本的解決**: lifecycle_score の幾何平均計算から usage を除外するか、children に最小 usage 値を与える設計変更が必要。もしくは、s_growth の mid-sampling 計算から j_child_survival を除外する（children が常に lifecycle_score=0 なのが仕様なら、収束判定には不適切）。

2. **j_reciprocity の計測・実装**: 現在のシミュレーションでは互恵性相互作用が発生しない。reciprocity メカニズムの実装または計測方法の再設計が必要。

3. **目的関数の再設計**: 現在の 6 因子乗算結合 J_kw_social は、一部の下位因子が常に 0 であるため実効的な次元が低下している。因子の取捨選択または重み付けの見直しが必要。

4. **収束判定の改善**: ttc=10 は「真の収束」ではなく閾値超過のアーティファクト。min_convergence_tick の導入または KW4_OBSERVATION_INTERVAL の大幅増加（例: 50 tick）が有効。

5. **HELP プロトコルセッション追跡の設計修正**: SimHelpSession/kw_sessions を collect_final_metrics に渡して正しく計測できるようにする。
