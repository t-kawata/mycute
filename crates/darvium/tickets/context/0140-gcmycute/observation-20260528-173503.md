# 観察レポート: 評判ベースGCのプロダクション実装とMYCUTE結合設計

## 1. 計装の実装状況

- 計装対象: Darvium::run_lifecycle_gc() の LifecycleScore→GC hazard→gc_state遷移→削除候補出力パイプライン
- 実装したテストコード: src/lib.rs (mod tests 内 T1-T5)
- 観測した統計量: 削除候補数、gc_state 遷移確認、空レジストリ/無効設定の境界値

## 2. 観測テスト実行結果

## 3. 較正ループ

本チケットでは較正は行わない（spec の「較正計画」より）。GC hazard パラメータはシミュレーションの phase4 から直接流用。

## 4. 現象の解釈（日本語）

GC パイプラインのプロダクション配線が完了した。DarviumConfig に gc_enabled/gc_interval/lifecycle_success_stub の3フィールドを追加し、run_lifecycle_gc() メソッドで WorkflowRegistry 内の全グラフに対して LifecycleScore→GC hazard→gc_state 遷移を実行する。HardDeleteCandidate 以上の gc_state に達したグラフを削除候補として返す。

観測された挙動:
- デフォルト GC hazard パラメータ（λ₀=1.0, γ_L=1.0, γ_B=0.1）では、信頼/評判が低いグラフが2回の GC 実行で Active→SoftDeleted→HardDeleteCandidate へと遷移する
- 空レジストリ・gc_enabled=false ではパイプラインが正しくスキップされる
- DualStoreCoordinator::delete_graph() で削除後ロードが NotFound エラーを返すことを確認

## 6. 次チケットへの示唆

- ConcreteEventBus の実装（別チケット）で GC イベント発行が可能になる
- MYCUTE 結合時は DarviumConfig { gc_enabled: true, gc_interval: 1000 } で設定し、適切な間隔で run_lifecycle_gc() を呼び出す
- GC の actual deletion は MYCUTE 側で削除候補リストを受け取り、DualStoreCoordinator::delete_graph() を呼び出す責務を持つ
