# 観察レポート: 本番 GC パスへの SubWorkflow 親生存ガード実装

## 1. 計装の実装状況
- 計装対象: compute_and_update_gc_state の parent_is_alive: Option<bool>
- 本番パス: parent_alive_map を事前構築し、親の gc_state が Active 以下なら子の gc_state 進行をブロック
- シミュレーションパス: #158 の phase4_gc_survival ガードで対応済みのため None

## 2. テスト実行結果
1394 passed, 0 failed

## 3. 現象の解釈（日本語）
本番 GC パス（Darvium::run_lifecycle_gc）では gc_state 機械（Protected→Active→SoftDeleted→HardDeleteCandidate→Tombstoned）によりグラフのライフサイクルを管理する。
本実装により、親が生存中（gc_state=Active または Protected）の子グラフは SoftDeleted 以上に進行しなくなる。親が死亡（gc_state≥SoftDeleted）した後は、子も通常通り GC 進行が可能になる。

## 4. 注意点
- parent_id: usize は WorkflowGraphId(String) の数値パースに依存しており、本番で正しく機能するには self-refinement 時に WorkflowGraphId が数値としてパース可能である必要がある
- 実際の本番運用で parent_id が設定されるかは別途 #158 の simulation.rs 側の設定が本番パスにも適用されるかに依存する

## 5. 目的関数 J(θ) の評価
- 本実装はガード条件追加であり、較正対象の定数は存在しない

## 6. 次チケットへの示唆
- 本番パスの parent_alive_map は registry.all_graphs() を毎 tick 走査するため、グラフ数が増えると O(n) のコストが発生する。大規模環境では親子関係のインデックス最適化が必要
