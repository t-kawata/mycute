## 3. 較正ループ

### 反復 1（初期値で確定）
- 仮説: CHIEFDOM_DEPTH_SCALE=3.0 は抽象化深度の正規化に適切なスケール。単一 SubWorkflow が depth=1 → 0.25 に正規化され、2段ネストが depth=2 → 0.4 に正規化される。このスケールで首長性スコアに十分な分散が生まれる。
- 変更定数: CHIEFDOM_DEPTH_SCALE = 3.0 (default)
- 観測結果: 境界値テストにおいて、空グラフ depth=0→0.0、単一 depth=1→0.25、2段 depth=2→0.4 を確認
- 解釈: depth=0→0.0、depth=SCALE=3.0→0.5、depth→∞→1.0 の期待通りの挙動。シミュレーション実運用時に首長選出が安定しない場合、SCALE を 2.0〜5.0 の範囲で調整可能。

## 4. 現象の解釈（日本語）

首長性スコアは評判スコア（直接互恵性・間接互恵性・経験値・継承の合成）と洗練スコア（グラフ構造の複雑さ）を50/50の重みで統合する。これにより、単に他人から信頼されているだけでなく、複雑なワークフローグラフを構築できる個体が社会的影響力を獲得する。

洗練スコアはさらに「抽象化割合」（SubWorkflow により隠蔽された内部ノードの比率）と「抽象化深度」（SubWorkflow ネストの深さ）の2軸で構成される。この2軸は翻訳可能性の観点から別関数としている。

Phase 3.7 を Phase 3.6（自己抽象化）の前に配置した理由は、自己抽象化によって SubWorkflow が増えると次 tick から抽象化割合と深度が変わるため、現在の tick のグラフ状態で首長性スコアを計算するためである。

## 6. 次チケットへの示唆

- 首長選出が安定しない場合（同一首長が維持される tick 数が短い場合）、CHIEFDOM_DEPTH_SCALE を調整して抽象化深度の寄与を変える
- 首長性スコアの重み（現在50/50）を将来的に動的調整可能にする場合、constants.rs に定数追加が必要
- 首長の特別な行動（首長のみ HELP プロトコル優先等）は本チケットのスコープ外だが、後続チケットで検討可能
