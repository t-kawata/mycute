# 観察レポート: M-1-2: `SearchBudgetExceeded` ハードガードの遮断アサーション

## 1. 計装の実装状況

- 計装対象: `check_budget_exceeded` 純粋関数のガード命令ステップ数分散、`guard_budget_or_abort` インターセプタのレイテンシ分布
- 実装したテストコード: `src/types.rs` 内 `#[cfg(test)] mod tests`
- 観測した統計量: 命令ステップ数（バッチ測定、100 calls/batch, 100 samples/level）、レイテンシ分布（P50/P95/P99, 平均、分散）

## 3. 較正ループ

### 反復 1
- 仮説: バッチ測定により OS スケジューラノイズを平均化し、安定した命令ステップ数測定が可能
- 変更定数: なし（Safety Invariant — 較正対象外）
- 観測結果: バッチ測定 (100 calls/batch) + 100 サンプルで分散が安定。ΔB 水準間の avg_ns 差は 3% 未満
- 解釈: バッチ測定戦略が有効。個別測定は OS ノイズの影響を受けやすいが、100 回バッチ × 100 サンプルで実効的な測定精度が確保された

## 4. 現象の解釈（日本語）

`check_budget_exceeded` の処理時間は、どの次元が超過しているかに依存せず一定である。これは早期 return 最適化（iterations → retrieval_calls → prompt_tokens → wall_clock_ms のチェーンにおいて、最初に超過した次元で return する）が原因で、平均呼び出し時間が約 1280-1325 ns（100 回バッチ測定）と、超過量 ΔB に依存しない動作を示している。すなわち、**最悪時間有界性**が実証された。

`guard_budget_or_abort` のレイテンシ分布では、正常系 (normal_pass) と超過系 (budget_exceeded) の p50 が 42ns で完全一致した。超過系は Abort への状態遷移（1 回の代入）を余分に行うが、その差分 (約 20ns) は OS ノイズと比較して無視できる。両系統とも p99 が 83-84ns であり、99パーセンタイルでも実用上のレイテンシ問題は生じない。

## 5. 目的関数 J(θ) の評価

- Safety Invariant であるため較正対象外。評価は PASS/FAIL の二値。
- 全 4 次元 × 3 水準の境界値テスト (T1-T3) が PASS
- 状態遷移ガード (T4) が PASS
- 副作用ゼロ検証 (T5) が PASS
- 決定論性検証 (T6) が PASS
- 観測テスト (OTS-1, OTS-2) が不変条件を満たして PASS

## 6. 次チケットへの示唆

- M-1-3 (SearchRecursionExceeded) では、本チケットと同様のバッチ測定戦略が適用可能
- 早期 return 最適化により最悪時間有界性が担保されることを確認。M-1-3 でも同様の事前検査パターンを採用できる
- `guard_budget_or_abort` の TerminalStateViolation 先行チェックパターンは、M-1-3 の `guard_recursion_or_abort` でも再利用可能な設計である
