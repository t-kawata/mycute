# 観察レポート: M1.5-R5 DarviumEventBus トレイト + FakeEventBus 実装

## 1. 計装の実装状況

- 計装対象: FakeEventBus の publish → replay 完全性 (n=1000), 並行アクセス下の clock 単調増加性 (n=64)
- 実装したテストコード: src/event.rs 内 test_eventbus_publish_replay_completeness_n1000, test_eventbus_concurrent_clock_monotonic_n64
- 観測した統計量: イベント消失率, clock 値の分布, clock 一意性

## 3. 較正ループ

本チケットは純粋なトレイト定義 + Fake 実装であり、較正すべき定数は存在しない。

## 4. 現象の解釈（日本語）

FakeEventBus の publish→replay 完全性テストでは、1000件のイベント一括発行に対して消失率 0% を確認した。また、64 スレッドからの並行 publish アクセス下でも clock 値の一意性が保たれており、Arc<Mutex<u64>> による排他制御が正しく機能していることを確認した。これにより RFC §12C.6 の MUST #1（単調増加）および MUST #6（全順序性）が満たされている。

## 5. 目的関数 J(θ) の評価

該当なし（較正対象の定数が存在しない）。

## 6. 次チケットへの示唆

- FakeEventBus は全ての EventBus テストの基盤として利用可能。後続の R6（VirtualClock 再定義）、R7（HumanChannel 再構成）のテストで活用できる
- InteractionId newtype は R7 の HumanChannel adapter でも必要となる
- 同期トレイトで設計したため、後続の ConcreteEventBus を async にする場合は破壊的変更となる可能性がある点に注意が必要
