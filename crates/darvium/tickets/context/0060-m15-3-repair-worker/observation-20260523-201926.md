## 3. 較正ループ

### 反復 1
- 仮説: REPAIR_SCAN_MAX_RETRY=3 は Safety Invariant として適切。30% FailingStore において、3回の再試行でほとんどの資産が回復可能。
- 変更定数: REPAIR_SCAN_MAX_RETRY=3, REPAIR_SCAN_BATCH_SIZE=100（新規追加）
- 観測結果: 無エラー環境で修復成功率 100%（OTS-1）。30% FailingStore で repaired=4,886 / quarantined=114（OTS-3）。初回スキャンで全資産が Committed または Quarantined に吸収され、減衰曲線は step 0 で即座収束（OTS-2）。
- 解釈: Safety Invariant としての定数設定は適切。REPAIR_SCAN_MAX_RETRY=3 は 30% エラー率に対して十分な再試行回数。REPAIR_SCAN_BATCH_SIZE=100 は現状の InMemory ストアでは実質的に無視される（バッチ分割の必要がない）が、実 DB 接続時には較正対象となる。

## 4. 現象の解釈（日本語）

**修復収束の即時性**: OTS-2 の減衰曲線が step 0 で即座に ln||E(t)||=0 に収束した理由は、startup_repair_scan() が内部的に apply_repair() を 1 回のスキャン呼び出し内で全資産に対して実行する設計による。各資産の修復試行は REPAIR_SCAN_MAX_RETRY=3 回の再試行を含むため、30% のエラー率でも 1 回のスキャン内で全資産が修復される（エラーが連続 3 回発生する確率は 0.3^3 = 2.7% であり、ほとんどの資産が修復可能）。したがって、複数回のスキャン呼び出しによる減衰曲線は観測されず、修復は 1 回のスキャンで完了する。

**吸収状態分布**: OTS-3 では 30% FailingStore 環境下で repaired=4,886 (97.72%)、quarantined=114 (2.28%) の分布が得られた。NeedsRepair に遷移した資産は修復成功で Committed、修復失敗（すべての再試行が成功しなかった場合）で Quarantined に吸収される。terminal_inconsistent=0 は、全資産が吸収状態に到達したことを確認している。Committed + Quarantined が初期不整合数と一致し、状態遷移の保存則が成立している。

## 5. 目的関数 J(θ) の評価

- 収束速度: 1 回のスキャン呼び出しで完全収束（即時）。J(θ) = 0（残余不整合ゼロ）
- 定常誤差: 0（全資産が吸収状態に到達）
- オーバーシュート: なし（修復は決定的かつ単調減少）
- 総合評価: Safety Invariant レベルの定数として適切。較正不要。

## 6. 次チケットへの示唆

- REPAIR_SCAN_BATCH_SIZE は InMemory ストアでは効果を発揮しない。実 DB 接続フェーズで真のバッチ処理が必要になった場合に較正対象とする。
- 減衰曲線が即時収束したことは、修復スキャンの設計において「スキャン呼び出し間の減衰」ではなく「1回のスキャン内の再試行分布」が支配的であることを示す。M1.5-2 の観測と同様、FailingStore のエラー確率を較正パラメータとして実環境の I/O エラー率に合わせた調整が必要。
- 真の並行アクセス（共有 RefCell → Mutex/Arc）はこのチケットのスコープ外。M1.5-3 のテストは独立インスタンスベースでロック競合やデッドロックの検出はカバーしない。
