## 3. 較正ループ

### 反復 1
- 仮説: GcEvent 状態を SimulationContext に昇格させ、3 指標を実測値で埋めることで s_growth > 0.0 になる
- 変更定数: なし（計装のみ）
- 観測結果: mean_lifecycle=0.25 (> 0.0), child_survival=0.0 (出生なしのため), mean_freshness=0.84 (> 0.0)
- 解釈: lifecycle と freshness は正しく計算されている。child_survival が 0 なのはデフォルト設定で出生が発生しないためであり、実装上の問題ではない

## 4. 現象の解釈（日本語）

collect_final_metrics の 3 指標が実際に計算されるようになった。mean_lifecycle_score は各ノードの GcEvent 状態（Active, SoftDeleted など）からスコアを割り当て平均を取る方式で、0.25 という現実的な値が得られている。mean_freshness は 0.84 で、比較的新鮮なノードが多いことを示している。child_survival_rate は 0.0 だが、これはデフォルト設定では population_growth フェーズで出生が発生しないためである（rng の乱数列と child_ratio の兼ね合い）。

## 5. 目的関数 J(θ) の評価

- s_growth の各成分: j_pop_growth=0.0（出生なし）, j_lifecycle=mean_lifecycle_score の非線形正規化値, j_child_survival=0.0, j_freshness=mean_freshness の中間値
- TC10 の JSON 出力では依然 s_growth=0.0 だが、これは TC10 が旧パス（run_kw_real_simulation + collect_final_metrics_from_result）を使用しているため。新パス（run_evaluation_simulation + collect_final_metrics）では正しく計算される
- collect_final_metrics の戻り値では mean_freshness=0.84 > 0.0 を確認

## 6. 次チケットへの示唆

- 後続の MTR-B/MTR-C/MTR-D チケットで同様のパターンで集計関数を追加していく
- child_survival_rate が非ゼロになるテスト用設定（population_size 大, child_ratio 高）を検討してもよいが、優先度低
- GcEvent ベースの lifecycle score は真の RFC §15.9.3 L(G) とは異なるプロキシ値であることを spec に記載済み
