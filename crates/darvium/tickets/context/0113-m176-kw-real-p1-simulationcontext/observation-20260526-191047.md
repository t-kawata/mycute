## 3. 較正ループ

### 反復 1
- 仮説: `remove_node` の範囲チェックに `population_count()` を使用すると petgraph の指数コンパクションにより不整合が生じるため、graph.remove_node() の戻り値で存在確認すべき
- 変更コード: remove_node のバリデーションを `if node_id >= population_count()` → `graph.remove_node(node_index).is_some()` に変更
- 観測結果: 1197/1197 テストが PASS
- 解釈: petgraph の `Graph::remove_node` は削除時に末尾ノードを穴に移動する（指数コンパクション）。そのため `population_count()` のみでの存在確認は不十分で、実際の削除結果を確認する必要がある。

### 反復 2
- 仮説: 観測テストで逆順削除（末尾→先頭）すれば指数コンパクションの影響を受けずに全ノードを削除できる
- 変更コード: 観測テストの削除ループを `node_ids.iter()` → `reverse_ids.iter()` に変更
- 観測結果: CSV 出力で全5ノードの削除が確認され、最終人口 = 10（初期値通り）
- 解釈: 逆順削除により各削除が常に末尾ノードを対象とするため、コンパクションによる ID 不整合が発生しない。

## 4. 現象の解釈（日本語）

Darvium はワークフローグラフの表現に petgraph の `Graph` を採用している。この型はメモリ効率を優先し、ノード削除時に内部のインデックスをコンパクションする。すなわち、N 個のノードを持つグラフから先頭に近いノードを削除すると、末尾のノードが削除された位置に移動し、その後ろのインデックスがずれる。

この動作は「ノード ID = petgraph インデックス」とする設計において重要な制約となる。キュー操作（FIFO）のように削除が常に末尾に対して行われるのであれば問題にならないが、任意のノードを削除する必要がある場合は以下の影響を考慮しなければならない：

- 削除後に生成されたノード ID の空間が連続でなくなる可能性
- 保持している NodeId が削除後に無効になる可能性
- ノードの集合をイテレートする際のスキップ処理

本チケット（P1: 基盤）ではこの制約を認識し、`remove_node` の実装では petgraph の戻り値で存在確認を行うことで安全に動作するようにした。後続チケット（P5: Lifecycle/GC）ではこの制約を踏まえた設計が必要になる。
