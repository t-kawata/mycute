# M1.76-20: 実験レポート生成と系列管理の統合

## Summary

M1.76-3 〜 M1.76-18 の全 16 チケットの実験結果を統合する `ReciprocityExperimentReport` 構造体と、それを Markdown / JSON 形式で出力するレポートライターを実装する。系列（lineage）管理により全実験に `exp-{yyyymmdd}-{seq}` ID を自動付与し、親子関係を追跡可能にする。

既存の `VillageExperimentReport`（M1.75-12）と同様のパターンに従い、reciprocity-awareness ドメインに特化したレポート基盤を提供する。

## Background

M1.76 フェーズ（reciprocity-aware survival and benevolence integration）では、16 のチケットにわたって多様な実験（純粋関数テスト、リプレイテスト、摂動テスト、プロパティベースファジング、較正スイープ、合成エコシステムシミュレーション、運用メトリクス観測、Phase 0-4 ロールアウト）が行われている。これらの実験結果は現状、各チケット内で個別に出力されており、相互の関連性を俯瞰できる統合レポートが存在しない。

以下の成果物を単一レポートに統合し、実験系列の全トレーサビリティを担保する必要がある：

- **M1.76-3〜M1.76-5**: Reciprocity score 計算の純粋関数検証結果
- **M1.76-6〜M1.76-11**: GC hazard・child protection・helper quality・remote exploration・growth・event injection の各パイプライン検証結果
- **M1.76-12**: 単調性テストスイート結果
- **M1.76-13**: 決定論的リプレイテスト結果
- **M1.76-14**: 摂動テストスイート結果
- **M1.76-15**: プロパティベース不変条件ファジング結果（failing seeds）
- **M1.76-16**: 多目的較正結果（目的関数値、最適パラメータ）
- **M1.76-17**: 合成エコシステムシミュレーション結果
- **M1.76-18**: 運用メトリクス観測結果
- **M1.76-19**: Phase 0-4 較正ロールアウト結果

### 参照観察レポート

- `tickets/context/0104-m176-19-phase-0-4-human-reviewed-calibration-rollout/observation-20260526-140153.md` — Phase 0-4 較正結果。最良 J(θ)=0.152755 (lambda_gc_base=0.1)、Phase 1 の非決定論問題、シミュレーション tick 数不足が示唆されている。

2. **`src/simulation.rs`** — `ReciprocitySimulationResult`（experiment_id 含む）、`generate_experiment_id()`、シミュレーションランナー

## Scope

1. **`ReciprocityExperimentReport` 構造体** — M1.76 ドメインの全実験結果を保持するレポート型
   - 実験 ID + lineage（既存 `ExperimentLineage` を再利用）
   - 要約統計量（既存 `ReciprocityOperationalMetrics` または同等の集約）
   - 較正結果（既存 `ReciprocityCalibrationReport` からの統合）
   - リプレイ結果一覧
   - 摂動結果一覧
   - 違反 seed 一覧（既存 `FailingSeedEntry` を再利用）
   - 最適パラメータ設定（既存 `BestKnownParams` を再利用）
   - Phase 0-4 通過状況
   - 未解決 anomaly リスト

2. **Markdown レポート出力** — `rules/darvium/experiment-reporting.md` の 8 セクションスケルトンに準拠した Markdown 生成

3. **JSON レポート出力** — experiment-reporting.md の JSON スキーマに準拠した JSON 出力

4. **実験 ID 自動生成の統一** — `ReciprocityCalibrationHarness::generate_experiment_id()` を標準化し、全実験で同一 ID 形式（`exp-{yyyymmdd}-{seq}`）を使用

5. **系列管理の統合** — 既存の `LineageStore`/`FsLineageStore` を介して全実験の lineage を永続化

## Non-scope

- レポートの Web UI 表示
- レポートの自動メール配信や通知

## Investigation

### 証拠 1: 既存レポート基盤の確認

`src/report.rs:247` — `VillageExperimentReport` 構造体は M1.75 ドメインの 4 実験系統（replay / perturbation / fuzzing / calibration）を統合する。Markdown 出力関数 `to_markdown()`（report.rs:311）は experiment-reporting.md の 8 セクションを全てカバーしている。

### 証拠 2: 較正レポートの分離

`src/calibration.rs:147` — `CalibrationReport`（village 用）および `src/calibration.rs:847` — `ReciprocityCalibrationReport`（reciprocity 用）は独立したレポート型として既に存在する。M1.76-20 ではこれらを統合する上位レポート型が必要。

### 証拠 3: 系列管理

`src/report.rs:76` — `ExperimentLineage` 構造体（experiment_id / parent_ids / description / tags / created_at）は M1.75-12 で既に実装済み。`LineageStore` トレイト（report.rs:135）と `FsLineageStore`（report.rs:151）も利用可能。M1.76-20 ではこれらを再利用する。

### 証拠 4: シミュレーション結果

`src/simulation.rs:218` — `ReciprocitySimulationResult` は `metric_series: Vec<SimulationTickSnapshot>` / `final_state` / `experiment_id` を持つ。各 tick の snapshot には `village_churn` / `helper_jsd` / `child_survival_rate` / `child_maturation_rate` / `helper_count_mean` / `help_sessions_active` 等が含まれる。

### 証拠 5: 観察レポートからの示唆

`observation-20260526-140153.md` より：
- Phase 0 純粋関数検証は全て PASS
- Phase 1 決定論的リプレイは全シードで Fail（非決定論 — 既知の制限）
- Phase 2 摂動テストは 2 種シードで PASS
- Phase 3 OFAT sweep: best J(θ)=0.152755 (lambda_gc_base=0.1)
- Phase 4: 上位 5 候補選択、human_review_ticket 生成成功
- 示唆: Phase 1 の非決定論問題の解消、シミュレーション tick 数増加、目的関数 λ 重みの実データ較正が必要

## 計装方法・観測対象

### 計装方法

- `src/report.rs` 内に `ReciprocityExperimentReport` 構造体とその出力関数を追加（既存 `VillageExperimentReport` と並列）
- 固定シード PRNG は使用せず（レポート生成は決定論的処理のため）
- 観測テストは `println!` + `--nocapture` で構造化出力を標準出力に書き出す

### 観測対象

- **必須フィールド充足率**: 全レポート出力で experiment_id / lineage / timestamp が常に存在すること（100% 要求）
- **空セクション耐性**: 空データでもセクションヘッダが出力され `(No data)` が表示されること
- **シリアライズ互換性**: JSON ラウンドトリップで全フィールドが一致すること
- **レポートサイズ**: 全フィールド設定時の Markdown/JSON 出力サイズを計測し、将来の拡張に対するベースラインとする

### 較正計画

本チケットはレポート基盤の実装であり、直接のパラメータ較正は含まない。ただし、実験系列の蓄積に伴う以下のメタ指標を観測対象とする：
- **未解決 anomaly 件数**: 各実験系列で報告された open_anomalies の累積数
- **best-known parameter bundle 更新履歴長**: パラメータ更新が発生した系列数
- **Phase 0-4 通過率**: 全 Phase が PASS した実験系列の割合

## Boy Scout Rule — 翻訳可能性計画

本チケットで触る `src/report.rs` について、以下の観点で改善する：

1. **関数名の統一**: Markdown 出力関数を `reciprocity_report_to_markdown` / `write_reciprocity_markdown_report` / `write_reciprocity_json_report` と命名。既存の `to_markdown` / `write_markdown_report` / `write_json_report` は Village 用に特化していることが自明になるようにする。
2. **責務の分離**: 既存の `to_markdown` 関数は Village 用と Reciprocity 用で分離する。単一の関数が両方の出力形式を担わない。
3. **定数化**: レポートのセクションヘッダ文字列（`"## Replay Metrics Summary"` 等）は定数として extract し、ハードコードの散在を防止する。ただし、使用箇所が限られているため過度な抽象化は避ける。
4. **既存コード尊重**: 既存の `VillageExperimentReport`・`to_markdown`・`write_markdown_report` は変更しない。M1.75 ドメインとの後方互換性を維持する。
