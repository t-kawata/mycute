# M-0.5-1: メモリ内デュアルストア候補抽出及び統合・重複排除器（Stage 2c）の検証

## Summary

SearchWorkflow Stage 2c において、2つの異種ストア（セマンティック検索 GraphStore / 構造検索 MetadataStore）から取得した `RankedCandidate` リストを統合し、重複排除（同一ワークフローIDの候補をマージ）する純粋関数 `merge_and_deduplicate_candidates` を実装する。本チケットでは当該関数のロジック検証と、重複排除アルゴリズムに統計的バイアスがないことの観測ベース検証を行う。

## Background

- **RFC §12.2 Stage 2c** に基づき、セマンティック検索結果 $K_{sem}$ 件と構造検索結果 $K_{struct}$ 件の候補リストを統合する。
- 同一ワークフロー（`workflow_id` 一致）が両ストアから返却される可能性があるため、重複排除（deduplication）が必要。
- 重複時のスコア統合ルール: 高い方の `blended_score` を残す（現在の仕様。将来的にブレンド方式に変更可）。
- 現状、`RankedCandidate` 構造体は `types.rs` に定義済みだが、統合・重複排除のロジックは未実装。
- **参照観察レポート**:
  - `tickets/context/0011-m-1-1-evaluatecandidatesstep/observation-20260522-203657.md` — M-1-1 決定境界分布観測結果
  - `tickets/context/0012-m-1-2-searchbudgetexceeded/observation-20260522-230022.md` — M-1-2 ハードガードレイテンシ観測結果
  - `tickets/context/0043-m-1-3-searchrecursionexceeded/observation-20260523-003310.md` — M-1-3 深さ制限ガード観測結果

## Scope

- `src/store/mod.rs` または `src/lib.rs` 経由で公開する `merge_and_deduplicate_candidates` 関数の実装
- 統合方法: `workflow_id` をキーとして `HashMap` に集約
- 重複時のスコア選択: 高い方の `blended_score` を残す（最大値保存則）
- セマンティック由来と構造由来の `provenance` は連結（重複除去なし）
- 非破壊的: 入力リストは変更しない
- テストコード: `src/store/mod.rs` 内の `#[cfg(test)] mod tests`
- 計装テスト（OTS）: カイ二乗検定によるバケット割り当ての一様性検証、最大値保存則の検証

## Non-scope

- 実DB（SQLite / LadybugDB）への永続化
- ブレンドスコア以外のスコア統合方式（加重平均・最小値選択等）
- スレッドセーフな並行マージ（単一スレッドの純粋関数に限定）
- M-0.5-2 のランクドリフト頑健性（本チケットは統合ロジックの正しさのみ）

## Investigation

### 既存コード調査結果

1. **`RankedCandidate` 構造体** (`src/types.rs:136-146`):
   - `workflow_id: String` — これが重複排除キー（UUID 相当）
   - `semantic_score: f64`, `structural_score: f64`, `blended_score: f64` — 3系統のスコア
   - `trust_score: f64`, `provenance: Vec<String>`, `metadata: serde_json::Value`
   - 現状、統合・重複排除のユーティリティ関数は未実装

2. **既存トレイト定義** (`src/store/mod.rs`):
   - `GraphStore` / `InMemoryGraphStore`: セマンティック検索担当
   - `MetadataStore` / `InMemoryMetadataStore`: 構造検索担当
   - いずれも `search()` メソッドを持ち `Vec<RankedCandidate>` を返却する想定

3. **テスト環境**:
   - `tests/` ディレクトリは未作成（M-0.5 フェーズから統合テストが追加される想定）
   - 本チケットは `src/store/mod.rs` 内のユニットテストで完結
   - 固定シード `StdRng::seed_from_u64(12345)` が利用可能（`TEST_PRNG_SEED`）

4. **`constants.rs`** (`src/constants.rs`):
   - 本チケットに関連する較正定数は存在しない（純粋関数実装のため）

### 設計判断

- **重複排除キー**: `workflow_id` を使用（UUID の役割を担う）
- **スコア統合ルール**: 最大値保存則（`max(blended_score_a, blended_score_b)`）。RFC §12.2 の「高い方のスコアが残る」仕様に従う
- **provenance 統合**: 両方のストア由来の情報を残すため連結（重複は許容）
- **戻り値順序**: 元のセマンティックリストの順序を維持し、構造リスト由来の要素を後方に追加（セマンティック優先順位）

## Test Plan

### T1: 正常系 — 重複なしマージ

セマンティック側 3件、構造側 2件（全件異なる `workflow_id`）。
期待値: 統合後 5件、各候補のスコアが元のまま維持されること。

### T2: 重複排除 — セマンティック側が高いスコア

セマンティック側の `blended_score=0.9`、構造側の `blended_score=0.7`、同一 `workflow_id`。
期待値: 統合後 1件、`blended_score=0.9`（最大値が残る）。

### T3: 重複排除 — 構造側が高いスコア

セマンティック側の `blended_score=0.6`、構造側の `blended_score=0.8`、同一 `workflow_id`。
期待値: 統合後 1件、`blended_score=0.8`。

### T4: 重複排除 — スコア同値

両方の `blended_score` が 0.75 で同一。
期待値: 統合後 1件、`blended_score=0.75`。

### T5: 境界値 — 両方空

セマンティック側 0件、構造側 0件。
期待値: 統合後 0件。

### T6: 境界値 — 片方のみ空

- セマンティック側 3件、構造側 0件 → 統合後 3件
- セマンティック側 0件、構造側 3件 → 統合後 3件

### T7: provenance 連結検証

同一 `workflow_id` で、セマンティック側 `["semantic-v1"]`、構造側 `["struct-v1"]`。
期待値: 統合後 `provenance = ["semantic-v1", "struct-v1"]`。

### T8: 大量候補マージ（パフォーマンス境界値）

セマンティック側 1,000件、構造側 1,000件（うち 500件重複）。
期待値: 統合後 1,500件、処理がパニックしないこと。

### T9: 入力非破壊性

マージ関数呼び出し後も元の `Vec<RankedCandidate>` の内容が変更されていないこと。

### OTS-1: カイ二乗検定によるバケット割り当て一様性

セマンティックリスト $K_{sem}$ 件、構造リスト $K_{struct}$ 件を PRNG で大量生成。統合後の `workflow_id` をハッシュバケット（バケット数 = 64）に割り当て、帰無仮説 $H_0$: スロット割り当ての確率は一様分布に従う に対するカイ二乗検定を実施。n = 10,000 イテレーションで p値の分布が $[0.0, 1.0]$ 上で一様であることを観測。

### OTS-2: 最大値保存則

同一 `workflow_id` の候補をランダムスコアで 10,000 組生成。各組で統合後の `blended_score` が入力の両方の値以上であることを検証（保存率 100% を期待）。

## 計装方法・観測対象

### 計装方法

- テストコード: `src/store/mod.rs` 内の `#[cfg(test)] mod tests`
- 計測プローブ: `println!` による構造化出力（`--nocapture` 経由で観測）
- PRNG: `StdRng::seed_from_u64(12345)` を使用（`rand::SeedableRng`）
- カイ二乗統計量: 手実装（外部クレートに依存しない）

### 観測対象

- **OTS-1（カイ二乗検定）**:
  - 観測量: $\chi^2$ 統計量、p値
  - サンプルサイズ: n = 10,000 イテレーション
  - 期待: p値の分布が一様分布に従う（アルゴリズムにバイアスがない証左）

- **OTS-2（最大値保存則）**:
  - 観測量: `blended_score` 保存率
  - サンプルサイズ: n = 10,000 組
  - 期待: 保存率 100%（安全装置として `assert!` で検証）

### 較正計画

本チケットの純粋関数に較正対象の定数は存在しない。ただし、計装テストのバケット数等は必要に応じて `constants.rs` に追加する可能性がある。

## Boy Scout Rule — 翻訳可能性計画

### 関数命名

```rust
pub fn merge_and_deduplicate_candidates(
    semantic: Vec<RankedCandidate>,
    structural: Vec<RankedCandidate>,
) -> Vec<RankedCandidate>
```

関数名だけで「セマンティック・構造の両候補リストをマージし重複排除する」ことが読み取れる。

### 内部実装方針

- `HashMap` によるグループ化（`workflow_id` をキー）
- 各グループの最大 `blended_score` を選出（`Iterator::max_by`）
- 元の順序を保持（セマンティック優先）
- 各責務は内部ヘルパー関数に分割（`group_by_id`, `select_highest_score`, `preserve_order`）

### 既存改善

- 現状の `RankedCandidate` は翻訳可能性を満たしている（フィールド名がドメイン概念を表現）
- 触る範囲が限定されているため大規模なリファクタリングは不要
