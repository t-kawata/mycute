# サーバー起動失敗に関する調査結果報告 (v2.2.24 / v2.3.24)

## 現象
インストーラーでインストールしたアプリをダブルクリックで起動した際、バックエンドサーバーが立ち上がらない（または立ち上がってもGUIと連携できない）場合がある。

## 根本原因の推定（証拠）
調査の結果、**macOSにおける「特権昇格（osascript）」時の環境変数の引き継ぎ不備と、それによる「HOMEディレクトリ（データベース保存先）」の不一致**が原因である可能性が極めて高いことが判明しました。

### 1. 特権昇格による実行ユーザーの変化
`src/utils/auth.rs` の 105行目付近（`spawn_elevated_server_macos`）において、macOSでは `do shell script ... with administrator privileges` を使用してサーバーを起動しています。このコマンドは、バックエンドサーバーを **root ユーザー** として実行します。

### 2. 環境変数 `$HOME` の不一致
`src/utils/my_path.rs` の 11行目付近（`get_mycute_home`）では、アプリケーションのデータ保存先（`.mycute`）を決定するために `std::env::var("HOME")` を参照しています。

- **GUI（一般ユーザー）**：`HOME = /Users/[ユーザー名]` -> `/Users/[ユーザー名]/.mycute/` を参照。
- **サーバー（root）**：`HOME = /var/root` -> `/var/root/.mycute/` を参照。

この結果、GUIが初期化したデータベース、設定（ポート番号など）、およびSSL証明書を、rootとして起動されたサーバー側が見つけることができず、不整合が発生します。

### 3. 引数でのパス情報の欠落
`src/mode/cl/main_of_cl.rs` の 1170行目付近（`manage_backend_server`）において、GUIからサーバーを起動する際の引数に、GUI側で解決済みのホームディレクトリ情報（`home_dir`）を渡す仕組みが存在しません。

```rust
// 現在の実装 (main_of_cl.rs)
let mut args = vec!["--parent-pid", &current_pid, "--skip-rt-migration"];
```

### 4. なぜ「時々（sometimes）」起きるのか
直近の修正（Direct Hosting対応）で導入されたロジックにより、**SSL証明書の信頼設定が必要な場合のみ特権昇格が行われる** ようになっています。
- **既に信頼済みの場合**：通常ユーザー権限で起動するため、GUIと同じ `$HOME` を参照し、正常に動作します。
- **新規インストールや証明書更新時**：特権昇格が必要になり、その際に root として起動されるため、上記のパス不一致問題が発生して起動に失敗します。

## 結論
GUIプロセス（一般ユーザー）からバックエンドサーバー（rootまたは一般ユーザー）へ、**常に同一のデータディレクトリを使用するようにパスを明示的に渡す仕組み**が欠けていることが、この不具合の直接的な証拠です。
