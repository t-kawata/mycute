# 質問への回答：なぜ「SendInputの一括送信」ではなく1文字ずつのばら売りになったのか？

ご記憶の通りです。ソースコードを確認したところ、過去に「一括送信（アトミック化）」で致命的な問題が発生し、苦肉の策として現在の「1文字ずつ送信＋Sleep処理」という泥臭い実装に落ち着いた歴史的経緯がコメントに明確に記録されていました。

**対象ファイル: `src/input/keyboard_win.rs` (137-140行目)**
```rust
// [フェーズ6] 1文字（コードユニット）ごとの分離送信ロジック
// DOWNとUPをアトミックに同時発射するとアプリが息継ぎできず文字抜けする。
// DOWN → Sleep → UP(無害化) → Sleep と自然なタメを復活させる。
// UP時に w_scan=0 を指定しているため、分離しても二重入力問題は再発しない。
```

### 過去に発生した具体的な問題点（なぜ一括送信がダメだったのか）

1. **対象アプリ側の「息継ぎ」不足による大量の文字抜け**
   - Windowsの `SendInput` で複数文字の `DOWN` と `UP` イベントを配列（`Vec<Input>`）に詰めて一括でAPIに投げると、OSはそれらを全く遅延なし（0ミリ秒間隔）で対象アプリケーションのメッセージキューに突っ込みます。
   - ブラウザ（Chrome系）やElectron、VSCodeなどの多くのモダンアプリケーションは、この「人間離れした遅延ゼロのキーストロークイベントの弾幕」を1フレーム内で処理しきれず、メッセージキュー上でイベントが破棄され、**結果的に激しい文字抜け**を引き起こしました。

2. **「二重入力バグ」の回避パッチとの相性の悪さ**
   - そもそもWindowsの `SendInput` には、Unicode入力時に `KEYUP` イベントを素直に送ると文字が2回入力されてしまう（二重入力）というOSレベルの有名なバグがあります。
   - その対策として、`KEYUP` 時には `w_scan=0` を送ってイベントを「無害化」する処理を入れています。しかしこれらを遅延ゼロで一斉送信すると、受け取り側のアプリが「どのキーのUPなのか」を見失い、入力がキャンセルされたり文字化けする要因になっていました。

これらの理由から、「DOWN → 待機 → UP → 待機」とすることで、**意図的にアプリケーションに処理時間（息継ぎ）を与えていた**というのが真相です。

---

### では、今回の「文字抜け」にどう立ち向かうべきか？

現在の `KEY_DELAY_MS_WIN = 5` （5ミリ秒）という設定は、「入力のもっさり感を消すための限界の速さ」を攻めた結果ですが、これでもまだPCの負荷や受け取り側のアプリの重さによっては「息継ぎ」に失敗し、今回のように「ん」が抜ける事象が発生してしまいます。

**現実的な解決策の選択肢:**

1. **微調整アプローチ（安全性重視）**
   - `KEY_DELAY_MS_WIN` を `5` から `10` 程度へと微増させ、文字抜けが発生しなくなるギリギリの妥協点に緩和する。
   - リスクは最小ですが、長い文を一気に入力する際に少し「パラパラパラ…」と入るもっさり感が増加します。

2. **クリップボード・インジェクション（Ctrl+V）方式の導入（確実性重視）**
   - 「キーボードのキーストロークをエミュレートする」こと自体に見切りをつけます。
   - 代わりに、文字列をOSのクリップボード（バックグラウンド保持）に入れ、対象アプリに対して `Ctrl + V` のキーイベント「だけ」を送信します。
   - 貼り付けであれば、1文字だろうと100文字だろうとアプリは「1回の挿入イベント」として処理するため、**文字抜けの発生確率は物理的にゼロ**になります。
